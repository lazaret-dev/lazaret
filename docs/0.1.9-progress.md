# 0.1.9 work in progress (branch `sources-langs-0.1.9`)

Started Oct 2, 2026 while 0.1.8 finishes on `rust-first`. Plan: `specs/lazaret-sources-and-languages-plan-2026-10-02.md` (project docs).

## Done

- **Go lexer** (`rust/crates/lazaret-engine/src/lex/go.rs`): `//` and `/* */` comments (no nesting), interpreted strings and runes, raw strings, numbers (hex floats, `_`, imaginary), Unicode names. An interpreted string or rune not closed on its line ends there; an unclosed comment or raw string runs to the end.
- **Rust lexer** (`rust/.../lex/rs.rs`): nested block comments, doc comments, strings that span lines, raw strings (`r#"…"#`), byte and C strings, characters and bytes told apart from lifetimes and loop labels, raw identifiers, numbers (`1..2`, `1.max(2)`, `1.5e-3f64`), a first-line shebang. Unclosed strings and comments run to the end of the text.
- `lex::structure(text, "go" | "rs", _)` returns comments, strings and literals, like the JavaScript and Python lexers.
- Tests: `lex/tests_go_rs.rs`, in a file of their own so `lex/tests.rs` is untouched.
- **Fuzzer for both lexers** (backlog item 4's first piece): `rust/crates/lazaret-engine/examples/fuzz_lex/` (`harness.rs`, `main.rs`), no external crates (CI's `check_rust_deps.py` allows none, so no libFuzzer). It builds programs from known tokens and mutates them, then checks: the program lexes back to exactly its tokens; cut at any token's start, the lexer returns the tokens before it; no panic, tokens in order, nothing outside a token but white space; a comment's or string's own text lexes to that one token; deterministic; `lex::structure` spans in order with no comment inside a literal; and linear time (200,000 characters of each opener that never closes). A failure prints its seed and iteration (`--seed S --iter I` reruns only it) and the smallest input that still fails.
  - Short gate: `lex/tests_fuzz.rs` (3 seeds x 1,500 programs per language, about a second), run by `cargo test` in CI's rust job.
  - Long runs: `cargo run --release --example fuzz_lex -- all --iters 300000 --seconds 60`. 300,000 programs and 900,000 mutants per language (41 and 54 million characters) found nothing past the bug below.
  - **First run found a real bug**: `'\'` repeated was quadratic in the Rust lexer (5 s for 200,000 characters), since a character literal looked for its line's end from every quote. Fixed (`quoted_line`: it stops at a line break as it reads).
  - Checked that it catches bugs: three injected ones (block comments that stop nesting, a raw string closing one `#` short, Go escapes not skipped) each failed at iteration 0.

- **P-3: `lazaret guard --from-plan pip install ...`** (`registry/guard.py`, tests in `tests/registry/test_guard_from_plan.py`). Opt-in. After pip's plan (`--dry-run --report`) is scanned, pip installs the scanned wheels from a folder (`--no-index --find-links`) instead of resolving and downloading a second time. On the profile's set (`requests boto3 pydantic`, `--target`, 2 vCPUs, cold verdict and pip caches, three runs each) the guarded install took 19.2 s at the median and 13.5 s with the flag; plain pip took 6.1 s. The trees `--target` receives are identical, byte for byte, with and without the flag.
  - **Why a folder and not `--no-deps --require-hashes` pins** (the backlog's first idea): pins would make pip mark every package as requested (the `REQUESTED` marker) and would need every pip option re-read. With the folder pip gets the user's own arguments (`-r`, `-c`, extras, `--target`, `--user`), so its own rules apply.
  - **Fails closed on the hash:** each file in the folder is hashed again just before pip runs and must be the one that was scanned; a file that is not is blocked, and `--trust` does not let it through. Pip then reads the file once more, so a local process running as the same user could still race that window.
  - **Falls back to the index** (with a line saying why) when the plan has a source distribution (it builds with requirements the index serves), a file too large to scan, an empty plan, or a folder that can't be made. uv is not covered (its second run is quick); other tools ignore the flag with a note.
  - **Left for later:** the remaining 13.5 s is mostly the plan itself (pip downloads and resolves through the index while it dry-runs): P-15's connection reuse and scanning while fetching are the next levers. For the release: CHANGELOG entry, README and `docs/` text for `--from-plan` (0.1.8 agent's files until the tag); decide then whether it becomes the default.

- **S-1: `lazaret [scan] github:owner/repo[@ref]` and `gitlab:group/project[@ref]`** (`registry/sourcescan.py`; `_cli.py` hands a command line with a `github:` or `gitlab:` argument to it; tests `tests/registry/test_sourcescan.py`, 41). `sources.checkout` resolves the ref to a commit and reads its archive into a directory; `sourcescan` runs the ordinary scan (`core.main`, every option) on it and removes the directory. `scan` as the first word is optional. Python only (the npm CLI has no sources). What it adds to a scan of a folder:
  - **The commit is named**: a `Source: github:o/r@<sha> (the ref v1)` line before the report, and report files named for it (`lazaret-github-o-r-0123456-report.json` and `.html`) in the current directory. The scan root is a temporary directory, so core's default (under the root) would lose them; `--out-dir`, `--json`, `--html` and `--sarif` still decide (the defaults are put in front of the user's options, so argparse's last-one wins), and the destination is checked before anything is fetched (exit 3, no request made). When every wanted report has an absolute path, `--out-dir` is not asked about.
  - **Fail closed on an incomplete read.** A path the archive left out (`export-ignore`), a tree too large to list, an archive that spent a budget, a file that could not be written: said on stderr after the report, and with `--ci` the exit status is 1 even when the gate passed. `--accept-incomplete` scans what was read and exits by the gate alone (and says so). Without `--ci` the exit status is the scan's, as for SC-TRUNCATED. A file only too large to read (`repo.MAX_MEMBER`) is a warning, not a gap: a scan of a folder does not read one either. This will fail `--ci` on every repository that uses `export-ignore` for its tests and `.github` (most PHP libraries do); see "Not covered".

The option table in `sourcescan.py` is held to `core.main --help` by a test (a new option in core that is missing there fails it).
  - Exit codes are the scan's; a spec that is not one, or a repository that cannot be fetched, is 2 (an unreadable target); a bug while fetching is `error: internal`, exit 5. The token and `LAZARET_GITLAB_URL` are read from the environment by `sources.py` only; the token is in no output (tested).

- **P-4: the timing helper, and `guard --timings`** (`scanner/timings.py`; tests `tests/scanner/test_timings.py`, 39, and `tests/registry/test_guard_timings.py`, 18). `with timings.span("engine", "scan_file"):` records seconds and a call under a phase and a name when a capture is open (`with timings.capture() as t, t.run():`), and costs one global read and a shared no-op object when none is.

- **P-15: connections that stay open between a guarded install's requests** (`registry/keepalive.py`, `guard.Fetcher`; tests `tests/registry/test_keepalive.py`, 89). Opt-in: `lazaret guard --keepalive pip install …`, off by default.
  - **Why:** `urllib` sends `Connection: close`, so each of the 25 to 50 requests of an install (index pages, `.metadata` files, the files) opens a TCP connection and a TLS session, where pip's own client reuses them: 48 connections for 48 requests in the profile's pip plan, 0.5 s of connect time summed here.
  - **The pool** (`keepalive.Pool`: thread-safe `http.client` connections; `Pool.request` is one GET that follows no redirect and adds no header). A connection goes back only when the body was read to its end and the server did not say `Connection: close` (an HTTP/1.0 answer without keep-alive and a body that ends with the connection count as closing); a response closed early closes its connection. A stale reused connection (`RemoteDisconnected`, a reset, a broken pipe, a TLS EOF) is dropped with its idle siblings and the GET is sent once more on a new connection; a new connection that fails is the caller's error. 30 s idle, 8 per (scheme, host, port, proxy). TLS is `ssl.create_default_context()`. A proxy from the environment is used for https as `urllib` uses it (one CONNECT through an `http://` proxy, `Proxy-Authorization` from the URL); any other proxy raises `Unsupported` and the fetch goes the `urllib` way as before; loopback is never proxied.
  - **What stays the guard's:** `Fetcher._open_kept` follows redirects by the rules of `_opener`: at most `repo.MAX_REDIRECTS`, `urllib`'s repeat rule (the fifth sight of a URL is refused; a test counts the requests on both paths), every target through `check`, a hop carrying only the credentials of its own URL. An answer that is neither 2xx nor a redirect is the same `FetchError` with `.status` and the same hints (`Fetcher._http_error`). `Fetcher.close()` closes the pool; the npm lockfile check, the uv check and `LocalIndex.close` call it (tested, also when a check raises). - **P-7: the guard's scans run in workers with limits, not in the guard's own process** (`registry/scanpool.py`, `guard.Scanner`; tests `tests/registry/test_scanpool.py`, 55, `test_guard_isolation.py`, 21, support module `_scanpool_support.py`). On by default; `--no-isolate` brings the old way back.
  - **Why:** with `--jobs 1` the scan ran in the process that downloads, holds every archive and talks to the package manager, and that process peaked at 2.15 GB on six large archives here (1.55 GB in the profile's install); and when a worker died the pool went on scanning in that same process. The hand-off also pickled the archive (copied three times, queued in the parent ahead of the worker).
  - **A file, not a pickle:** the parent writes the bytes to a directory of its own (mode 0700; a file named `<sha256>-<n>.bin`, mode 0600) and sends the worker the path. The worker reads the file and hashes it again: bytes that are not the ones staged make the scan fail (`ArchiveChanged`), never a verdict on other bytes. The file goes as soon as the answer is in, the directory when the pool closes. The digest in the name is what a seen-set shared by the workers (P-2a's guard half) or an in-flight table keyed by digest needs; neither is written.
  - **Limits that follow the work:** each worker sets once an address-space limit (`RLIMIT_AS`, default 6144 MB, `--worker-memory MB`, 0 for none; Linux only, ignored elsewhere), and for each archive the parent says how many engine threads it may use: the cores shared out among the archives running at that moment (all of them for one big archive alone, half each for two), so `--jobs` times engine threads stays within the cores. The worker then sets a CPU-time limit (`RLIMIT_CPU`) above the scan's own deadline as a backstop for a scan that ignores it. `engine.THREADS` is a module global the engine reads at each call; the pool is the only writer.
  - **What a lost worker means:** every archive in flight in that pool is run once more, alone, in a pool of its own. One that kills its worker again raises `Died`, and the guard blocks that package as "could not be checked" (`--trust` lets it through, as for any scan that fails). The work split said INCOMPLETE; the guard has no such verdict, and "blocked, not cleared" is what the guard does with a scan error, so that is what this is. A scan that does not answer within the wall limit (`2 * timeout + 60`) gets the pool's processes terminated and raises `Hung` ("the scan did not finish", as before). After `MAX_BREAKS` (20) lost workers the pool starts no more and raises `Died`, never scanning in the guard's own process.
  - **A pool that cannot start is told apart from one that loses a worker:** the first pool is proved by one trivial job. If that fails (no `spawn`, a limit too small to import Python, a frozen program), `Unavailable`, and the guard scans in its own process from then on and says so once (`lazaret guard: no scan worker could be started; scanning in this process`).
