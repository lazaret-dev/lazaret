# 0.1.9 work in progress (branch `sources-langs-0.1.9`)

Started Oct 2, 2026 while 0.1.8 finishes on `rust-first`. Plan: `specs/lazaret-sources-and-languages-plan-2026-10-02.md` (project docs).

## Done

- **Go lexer** (`rust/crates/lazaret-engine/src/lex/go.rs`): `//` and `/* */` comments (no nesting), interpreted strings and runes, raw strings, numbers (hex floats, `_`, imaginary), Unicode names. An interpreted string or rune not closed on its line ends there; an unclosed comment or raw string runs to the end.
- **Rust lexer** (`rust/.../lex/rs.rs`): nested block comments, doc comments, strings that span lines, raw strings (`r#"…"#`), byte and C strings, characters and bytes told apart from lifetimes and loop labels, raw identifiers, numbers (`1..2`, `1.max(2)`, `1.5e-3f64`), a first-line shebang. Unclosed strings and comments run to the end of the text.
- `lex::structure(text, "go" | "rs", _)` returns comments, strings and literals, like the JavaScript and Python lexers.
- Tests: `lex/tests_go_rs.rs`, in a file of their own so `lex/tests.rs` is untouched.
- **Fuzzer for both lexers** (backlog item 4's first piece): `rust/crates/lazaret-engine/examples/fuzz_lex/` (`harness.rs`, `main.rs`), no external crates (CI's `check_rust_deps.py` allows none, so no libFuzzer). It builds programs from known tokens and mutates them, then checks: the program lexes back to exactly its tokens; cut at any token's start, the lexer returns the tokens before it; no panic, tokens in order, nothing outside a token but white space; a comment's or string's own text lexes to that one token; deterministic; `lex::structure` spans in order with no comment inside a literal; and linear time (200,000 characters of each opener that never closes). A failure prints its seed and iteration (`--seed S --iter I` reruns only it) and the smallest input that still fails.
  - Short gate: `lex/tests_fuzz.rs` (3 seeds x 1,500 programs per language, about a second), run by `cargo test` in CI's rust job.
  - Long runs: `cargo run --release --example fuzz_lex -- all --iters 300000 --seconds 60`. 300,000 programs and 900,000 mutants per language (41 and 54 million characters) found nothing past the bug below.
  - **First run found a real bug**: `'\'` repeated was quadratic in the Rust lexer (5 s for 200,000 characters), since a character literal looked for its line's end from every quote. Fixed (`quoted_line`: it stops at a line break as it reads).
  - Checked that it catches bugs: three injected ones (block comments that stop nesting, a raw string closing one `#` short, Go escapes not skipped) each failed at iteration 0.

- **P-3: `lazaret guard --from-plan pip install ...`** (`registry/guard.py`, tests in `tests/registry/test_guard_from_plan.py`). Opt-in. After pip's plan (`--dry-run --report`) is scanned, pip installs the scanned wheels from a folder (`--no-index --find-links`) instead of resolving and downloading a second time. On the profile's set (`requests boto3 pydantic`, `--target`, 2 vCPUs, cold verdict and pip caches, three runs each) the guarded install took 19.2 s at the median and 13.5 s with the flag; plain pip took 6.1 s. The trees `--target` receives are identical, byte for byte, with and without the flag.
  - **Why a folder and not `--no-deps --require-hashes` pins** (the backlog's first idea): pins would make pip mark every package as requested (the `REQUESTED` marker) and would need every pip option re-read. With the folder pip gets the user's own arguments (`-r`, `-c`, extras, `--target`, `--user`), so its own rules apply.
  - **Fails closed on the hash:** each file in the folder is hashed again just before pip runs and must be the one that was scanned; a file that is not is blocked, and `--trust` does not let it through. Pip then reads the file once more, so a local process running as the same user could still race that window.
  - **Falls back to the index** (with a line saying why) when the plan has a source distribution (it builds with requirements the index serves), a file too large to scan, an empty plan, or a folder that can't be made. uv is not covered (its second run is quick); other tools ignore the flag with a note.
  - **Left for later:** the remaining 13.5 s is mostly the plan itself (pip downloads and resolves through the index while it dry-runs): P-15's connection reuse and scanning while fetching are the next levers. For the release: CHANGELOG entry, README and `docs/` text for `--from-plan` (0.1.8 agent's files until the tag); decide then whether it becomes the default.

- **S-2, offline half: workflow hardening checks** (`scanner/ghworkflow.py`: `hardening(text)` and `hardening_rule(kind, detail)`; npm twin `js/src/lib/ghworkflow.js`; tests `tests/scanner/test_ghworkflow_hardening.py` and `tests/architecture/test_js_parity_workflow_hardening.py`). `hardening` returns `(kind, line, detail)` by line; `hardening_rule` gives the rule (`id, name, type, sev, msg, why, fix, ref`) that `core.mk_issue` takes. Six kinds, five rule ids:
  - `unpinned` -> `SC-WORKFLOW-UNPINNED`: a `uses:` of an action, a reusable workflow or an image that is not a full commit SHA or a digest. MAJOR; MINOR for GitHub's own actions (`actions/`, `github/`) at a version tag.
  - `pr-checkout` -> `SC-WORKFLOW-PR-CHECKOUT` (CRITICAL): a `pull_request_target` job that checks out the pull request: `actions/checkout` with a `ref:` or `repository:` taken from the PR head, `git checkout/fetch/switch/pull/merge/cherry-pick` with a PR ref, and any `gh pr checkout`.
  - `cache` -> `SC-WORKFLOW-CACHE`: a cache restored in a release workflow (event `release`, an OIDC grant, a publish action or a publish command). MAJOR when asked for (`actions/cache`, `cache: npm`), MINOR when a setup action does it by default.
  - `perms` and `perms-missing` -> `SC-WORKFLOW-PERMISSIONS`: a write scope (or `write-all`) for every job (MAJOR); no `permissions:` at the top and a job with none of its own (MINOR).
  - `oidc-install` -> `SC-WORKFLOW-OIDC-INSTALL` (MAJOR): a job that can request an OIDC token (its own `permissions:`, or the workflow's when it has none) and installs dependencies without `--ignore-scripts`.
  - **`findings()` is untouched** (its `secrets` and `backdoor` kinds): `core.workflow_issues` and `scan.js workflowIssues` send any other kind to the backdoor branch, so the new kinds are reported apart and wired in by S-4 (wire-up item 6).
  - **Commands are read where a command starts** (line start, after `; & | (`, `then/do/else/sudo/time/exec/command`, after `VAR=value` words), so `echo npm ci` and a commit message that names it are not installs.
  - **Linear time**: the first version was quadratic in the number of jobs (4,000 jobs: 11.7 s); permissions are now read in one pass and steps grouped by job (16,000 jobs, 2 MB: 0.56 s in Python, 0.2 s in JS). Adversarial lines (`;a=b` x 50,000, 200,000 spaces after `git`, ...) are in the tests.
  - Checked: the Python and JS results and rules are equal on 1,500 generated workflows plus the curated ones (the pattern text and lists are compared too); eight injected twin bugs were each caught; 39 unit tests; the existing persistence tests (outline and findings) unchanged.
  - **Not covered**: `workflow_run` checkouts, script injection through `env:`, YAML anchors, what a repository's default token permission is (so `perms-missing` stays MINOR).
  - **Left for the online half**: `registry/actions.py` (resolve each `uses:` at its pinned SHA through `sources.py`: moved tag, impostor commit, tag off the default branch).

- **S-2, online half: what a workflow's `uses:` really point to** (`registry/actions.py`; `ghworkflow.uses()` and `parse_uses()` give it the lines; tests `tests/registry/test_actions.py` against an in-memory GitHub, `tests/registry/_actions_support.py`, which S-1 and S-4 can reuse). Python only: it is a registry module, there is no npm twin. `python -m lazaret.registry.actions [--no-pins | --pins FILE] [--accept-moved] [--max-calls N] WORKFLOW...` prints the report (exit 1 a finding, 3 something unchecked, 2 usage). Six kinds, six rule ids (`actions.rule(kind, detail)` builds the rule as `hardening_rule` does):
  - `impostor` -> `SC-ACTION-IMPOSTOR`: a pin that is in no branch and at no tag tip of the repository (GitHub resolves a fork's commit under the parent's name). CRITICAL when every tag tip and every branch was compared, MAJOR when the repository has more than 100 tags or branches, or more than 9 branches (the default branch, then release branches, are compared first), and the message says what was not looked at.
  - `tag-moved` -> `SC-ACTION-TAG-MOVED` (CRITICAL): a version tag (`v4.1.0`, not `v4`) that points to another commit than when it was first seen. What was seen is kept in the pin book (`~/.cache/lazaret/actions-pins.json`, `LAZARET_ACTIONS_PINS`, `--pins`): the first sighting is no finding, a moved tag keeps its first entry so the alert stays until `--accept-moved`, and a missing book only finds less. Floating tags are left alone.
  - `off-branch` -> `SC-ACTION-OFF-BRANCH` (MAJOR): a tag whose commit is in none of the branches compared.
  - `pin-mismatch` -> `SC-ACTION-PIN-MISMATCH` (MAJOR): `@<sha> # v4.1.0` where v4.1.0 points elsewhere or is no tag (comments `# v1.2.3`, `# tag=v1.2.3`, `# ratchet:o/r@v1.2.3`; a floating `# v4` says nothing).
  - `docker-unpinned` -> `SC-ACTION-DOCKER-UNPINNED` (MAJOR) and `nested-unpinned` -> `SC-ACTION-NESTED-UNPINNED`: read from the action's `action.yml` at the commit (a Docker image without a digest; a composite action's steps that are not pinned, and those looked at in turn, two levels deep, with the chain in `via`).
  - **Says what it did not check**: a GitHub refusal (the rate limit: 60 an hour without `GITHUB_TOKEN`), the call budget (45 without a token, 400 with), an expression in a ref, a path that cannot go in a URL, a repository it cannot see are `incomplete`, so the action is not cleared; the run stops asking after a rate-limit answer. A pinned release costs two calls (tag list, `action.yml`); an untagged pin about five.
  - **Rules of `sources.py`**: HTTPS to `api.github.com` only, names from the workflow validated before they are put in a URL, token only to the API host and in no report, bounded responses.
  - Checked: 54 tests; 20 injected bugs, each caught. Against the real API (read through a web fetch, since the sandbox has no GitHub credentials): the tag list's shape and `compare`'s `status` ("behind" for a release commit against main) are as the code reads them; `git/ref/tags/...` answered 403 through that route, so its shape is the documented one and untested live. **A live run with a token is the check still to make.**
  - **Not covered**: scanning the action's own code (a JavaScript `main`, `pre` and `post` like an npm package, a composite's `run:` as shell: that needs `sources.checkout` and the engine, so S-1/S-4), a Dockerfile's `FROM` lines, GitHub Enterprise Server, nested `uses:` comments, the content of a reusable workflow.
  - **For S-4/S-1**: the CLI can print `rules` for each finding; the six `SC-ACTION-*` ids need README, `docs/DESIGN.md` and CHANGELOG lines, and a network scan reports them only when the user asked for the online checks.

## Backlog (profile of Oct 3)

Full profile, tables and the prioritized backlog: the Lazaret.dev project, `audits/lazaret-profile-and-backlog-2026-10-03.md`. In short, on the 2-vCPU sandbox:

- The engine is 37 to 89% of a registry scan; archive reading 2 to 12% (botocore 41%); other Python 6 to 19% on the big packages. Porting `repo.py` or `guard.py` to Rust does not pay now.
- `import_time_risk` runs at 3 to 5 MB/s (3 to 6 times slower than `scan_file`) and is 54 to 80% of engine time. The review of the profile (`audits/lazaret-profile-review-2026-10-03.md`) found why: its data-flow analysis (60% of a Python file's call), not re-reading files. SC-USE-RISK reads files for at most 3 s per artifact, so on next it reads 28% of its input; findings on large bundles depend on machine speed.
- litellm ships 8 release files (1.102.0, 1.103.0 and 1.103.2 alike); 25% of their bytes are unique, so dedupe by content hash within a run cuts that scan from 76 s to about 26 s (estimate). Adjacent versions repeat 51 to 92% of bytes (the persistent cache, which must not be trusted across refs).
- `guard pip` runs pip twice: 19.95 s against 6.23 s plain, scanning 1.9 s of it. `guard npm`, cold: 44.3 s against 19.8 s plain; with the verdict cache 20.5 s.
