target list (`fuzz_targets.KNOWN`) and the project doc `audits/lazaret-fuzz-findings-2026-10-03.md` use them.

replayed with `python3 scripts/fuzz/fuzz.py --replay FILE TARGET` (the file is what `--findings DIR` wrote), or with the

## F-1  safexml: an encoding expat does not know is not a `ParseError`

**See it.**

```python
from lazaret.safexml import ElementTree as ET
ET.fromstring(b'<?xml version="1.0" encoding="T7"?><a/>', forbid_dtd=True)      # LookupError: unknown encoding: T7
ET.fromstring(b'<?xml version="1.0" encoding="UTF32"?><a/>', forbid_dtd=True)   # ValueError: multi-byte encodings are not supported
```

Fuzz: target `xml` and `xml-minidom`, seed 0 runs 57–58 and 166 (34- and 35-byte inputs; the two above are the smallest);
`--replay` of each file. The same on 3.10 (checked on the device) and 3.13: the exception comes out of `expat`'s `Parse`,
which `safexml/ElementTree.py` (`feed`, `close`) wraps only for `expat.error`, and which minidom's `ExpatBuilder`
(`parseString`, `parseFile`) does not wrap at all. This is what the standard library's `xml.etree` and `xml.dom.minidom`
raise for these inputs too, so `safexml` is a faithful drop-in here; what is missing is the promise that makes it
*safe* to call: one exception type for hostile XML.

**Cost.** Everything that parses with `safexml` and catches only `SafeXMLError` / `ParseError` is ended by it.
`repo.pypi_latest_from_feed` is the one that does (it catches those two only, so a feed that names a bad encoding raises
`LookupError` / `ValueError` out of an install-time lookup). `repo._parse_xml` catches `ValueError` but not `LookupError`
(the `UTF32` input becomes a `FeedError`, the `T7` one does not); its watchlist caller catches `Exception`, so there it is
a skipped feed. Low: the feed is PyPI's, over TLS, and the declaration is written by PyPI. It is a hardening gap in the layer
whose job is to be the one place that turns hostile XML into one exception type.

**Fix (the owner's choice).** Either keep the stdlib's behaviour in `safexml` and say so in its docs (unsupported
encodings raise `LookupError` / `ValueError`, as the stdlib does), and make the two `repo.py` callers catch them
(`pypi_latest_from_feed`: add `LookupError, ValueError`; `_parse_xml`: add `LookupError`); or normalise in `safexml`:
`except (expat.error, LookupError, ValueError)` in `feed` / `close` and in the minidom builder, raising the `ParseError` /
`SafeXMLError` the `expat.error` branch raises, without echoing the encoding name (hostile text). The second is the
stronger one; it changes what `safexml` raises, so it belongs with the provisional-API note. Either way, add the two inputs
above to the safexml tests. When fixed, delete the four `xml` / `xml-minidom` lines of `fuzz_targets.KNOWN`; the fuzz job
then fails on a regression.

## F-2  zip entries that overlap: a warning on stderr and no anomaly

**See it.** Two stored entries whose central-directory records give the same local-header offset:

```python
import io, warnings, zipfile
from lazaret.registry import repo

buf = io.BytesIO()
with zipfile.ZipFile(buf, "w", zipfile.ZIP_STORED) as zf:
    zf.writestr("a.py", b"x = 1\n")
    zf.writestr("b.py", b"y = 2\n")
data = bytearray(buf.getvalue())
first = data.find(b"PK\x01\x02")                       # the two central-directory records
second = data.find(b"PK\x01\x02", first + 4)
data[second + 42:second + 46] = data[first + 42:first + 46]     # b.py now starts where a.py does
anomalies = []
with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    print([(m[0], m[3]) for m in repo.iter_archive(bytes(data), "zip", "wheel", anomalies=anomalies)])
print(anomalies, [f"{w.category.__name__}: {w.message}" for w in caught])
# [('a.py', None), ('b.py', 'corrupt')]
# [] ["UserWarning: Overlapped entries: 'a.py' (possible zip bomb)"]
```

Fuzz: target `archive-zip`, seed 0 run 490 (911 bytes), and again in the long run (seed 12). The warning is CPython's
(3.12.3 and 3.13 on): on the device's 3.10 nothing is warned, `b.py` is `corrupt` all the same, and the anomalies list is
empty all the same, so the missing anomaly is the finding on every version and the warning is the extra on new ones.

**Cost.** Overlapping entries are the shape of a zip bomb; the reader does flag the second entry `corrupt`, but the
archive's anomalies list stays empty, so the scan does not report "this archive overlaps its entries" as a finding of its own, and
the warning goes to stderr (a line in a user's terminal, unexplained, from a hostile package). Under `-W error` (a host
that turns warnings into errors, a test runner) `UserWarning` is not one of `_ZIP_READ_ERRORS`, so it propagates out of
`iter_archive`. Low.

**Fix.** In `_iter_zip`'s `read`, run `zf.open(info)` inside `warnings.catch_warnings(record=True)` (`simplefilter("always")`),
turn an "Overlapped entries" warning into `anomalies.append(("overlap", info.filename, "entries overlap (possible zip bomb)"))`
and keep the member `corrupt`; add the snippet above as a test (skip it where `zipfile` does not warn). When fixed, delete the
`archive-zip` line of `KNOWN`.

## F-6  a zip entry with no name: `IndexError` on Python 3.10, silently skipped on 3.11+

**See it.** A zip with two stored entries, `a.py` and one whose name is empty (the standard library of 3.10 cannot write
such a zip, so the fixture is bytes: `NAMELESS` in `tests/architecture/test_fuzz_scripts.py::VersionBoundFindings`):

```python
from lazaret.registry import repo
from tests.architecture.test_fuzz_scripts import VersionBoundFindings
list(repo.iter_archive(VersionBoundFindings.NAMELESS, "zip", "wheel", anomalies=[]))
# Python 3.10.12: IndexError: string index out of range   (zipfile.py, ZipInfo.is_dir: self.filename[-1] == '/')
# Python 3.13.16: [('a.py', None, ...)]; the nameless entry is not read, and no anomaly says so
```

Found by the fuzzer on Python 3.10 (target `archive-zip`, seed `x1`, run 47, shrunk to 463 bytes). The 3.13 run never
sees it; the weekly job's 3.10 half does.

**Cost.** `_iter_zip` calls `info.is_dir()` before it looks at the name, and `is_dir` of 3.10 (and before) indexes the last
character. `IndexError` is not one of `_ZIP_READ_ERRORS`, so one such entry in a wheel or a zip sdist raises out of
`iter_archive`, through `_scan_artifact`, instead of becoming a finding about the archive. On 3.11+ the entry is dropped
silently (its name is canonicalised to nothing), so content in a nameless entry is neither reviewed nor reported.

**Fix.** In `_iter_zip` test the name first: `if not info.filename:` record `anomalies.append(("path", info.filename, "empty name"))`
and `continue`, before `info.is_dir()`; both Pythons then give the same answer (the member is not read, and the archive says
why). Then delete the `IndexError@repo.py` line of `KNOWN` and `test_f6_a_zip_entry_with_no_name_raises_index_error_before_python_3_11`.

## F-7  a zip entry that declares a 4 GiB LZMA dictionary: `MemoryError` where memory is capped

**See it.** `VersionBoundFindings.HUGE_DICTIONARY` in `tests/architecture/test_fuzz_scripts.py` (625 bytes: a wheel whose
entries are method 14, LZMA, and whose raw-LZMA header says `5d 00 83 ff fb`, a dictionary of 0xfbff8300 bytes). With the
address space capped, as in a container or a CI job with a memory limit:

```python
import resource, sys
resource.setrlimit(resource.RLIMIT_AS, (2 << 30, 2 << 30))
from lazaret.registry import repo
list(repo.iter_archive(HUGE_DICTIONARY, "zip", "wheel", anomalies=[]))        # MemoryError, out of `read` in `_iter_zip`
```

Without a cap, Python 3.13 on a large machine reads it (every LZMA entry `corrupt`, 27 MB peak: the dictionary is allocated
but not touched); the device's 3.10 VM raised `MemoryError` with no cap set. Fuzz: target `archive-zip`, seed 21, run 25708 (625
bytes), on the device. `zipfile`'s `_LZMADecompressor` builds `lzma.LZMADecompressor(FORMAT_RAW, filters=[…])` on the first
read of the entry, and the allocation is asked for before a byte of the entry is decoded.

**Cost.** `MemoryError` is not in `_ZIP_READ_ERRORS`, so it leaves `iter_archive` (and `_scan_artifact`): one 625-byte wheel
ends the review of a package on any host whose memory is limited, where a hostile package should end as a finding. On a host with
no limit the process asks the kernel for 4 GiB of address space per entry and gets it (nothing is touched), so it is the
capped hosts that fail, and they are the ones that cannot spare the memory for a second try.

**Fix.** Either, or both: add `MemoryError` to `_ZIP_READ_ERRORS` so the entry is `corrupt` with a detail; and refuse an
LZMA entry before decoding it. Wheels may use stored or deflated entries only (PEP 427), so a method-14 entry in a wheel is
already an anomaly worth reporting; for a zip sdist, read the 9 bytes after the local header (version, length of the
properties, the 5 property bytes) and refuse a dictionary over some bound (64 MiB is generous). When fixed, delete the `MemoryError@repo.py` line of `KNOWN` and
`test_f7_a_huge_lzma_dictionary_is_a_memory_error_where_memory_is_capped`.

## F-3  sca: an include with a NUL byte in a requirements file  (fixed)

**See it (before the fix).** A `requirements.txt` of `-r\x00` made `os.path.realpath` raise `ValueError: embedded null byte`
inside the include reader, and with it `scan_all`, so one hostile file ended the whole inventory. Fuzz: target
`sca-requirements-txt`, seed 0 run 8, three bytes (`-r` NUL).

**Fix.** `_scan_requirements` treats an include path with a NUL as "not found" (counted in the existing
`requirements includes not found` warning) before it reaches `realpath`; the rest of the file and the other includes are read.
Tests: `tests/scanner/test_sca_fuzz_findings.py::NulInAnInclude`.

## F-4  sca: a deeply nested TOML file raised `RecursionError`  (fixed)

**See it (before the fix).** `x = [[[[…` (or `[[[[…`, or inline tables in inline tables) a few hundred levels deep:
`tomllib` (3.11+) raises `RecursionError`, which `sca.load_toml` did not turn into the `ValueError` its callers catch.
Callers hit: `scan_all` for `uv.lock`, `poetry.lock`, `pylock.toml` and `pyproject.toml`, the guard's `uv_lock_packages`,
and the package-manager settings readers. On 3.10 the subset parser already refused it as `ValueError`. Fuzz: target
`sca-uv-lock`, seed 0 run 138 (496 bytes, nesting of `[`). `repo._pep517_backend` already caught `RecursionError`.

**Fix.** `load_toml` maps `RecursionError` to `ValueError("TOML: RecursionError")`. Tests: `DeepToml` in the same test file
(each reader warns `unparseable <name> file(s)` and goes on; the guard's reader returns no packages).

## F-5  sca: `setup.py` with an invalid escape printed a `SyntaxWarning`  (fixed)

**See it (before the fix).** `setup.py` text such as `install_requires=['a\d==1']` (a docstring of `\d+` does the same):
the reader compiles the file to read its literals (it never runs it), and Python 3.12+ prints
`SyntaxWarning: invalid escape sequence '\d'` on stderr; under `-W error` the compile raised and the file was read by its tokens
instead (the same answer for these inputs, by another path). Fuzz: target `sca-setup-py`.

**Fix.** `_setup_py_requirements` parses inside `warnings.catch_warnings()` with `simplefilter("ignore")`, and leaves the
caller's filters as they were. Tests: `SetupPyWarnings`.

## F-8  registry modules: an error message that quotes odd characters was over 1,200 characters  (fixed)

**See it (before the fix).** `Crates().check_version("\udcff" * 500)` or `Go().check_version("\U0010ffff" * 500)` raised a `SpecError`
whose message held `repr(text[:120])`: every such character is escaped to 6 to 10 characters, so the message was 720 to 1,200
characters, over the 600 the module contract allows ("a sentence, not a copy of the input"). Fuzz: target `ecosystem-names`
(`names-message`, seed 2, run 826); the contract now has such names and versions in `base.HOSTILE_NAMES` and
`base.HOSTILE_VERSIONS`.

**Fix.** `base.show` cuts the text until its `repr` fits the limit (plus the quotes), not before it is escaped. Tests:
`test_ecosystems_base` (`show`) and the contract's hostile-name and hostile-version tests for every module.

## F-9  Go: a zip whose members start at one place made CPython warn on stderr  (fixed)

**See it (before the fix).** A module zip in which two central-directory entries have one local header offset: `zipfile` of
3.12.3 and later warns `Overlapped entries ... (possible zip bomb)` when the second is opened, from inside `zip_h1`. Go reads
such a zip; no module zip is one (the proxy builds them with `CreateFromVCS`). Fuzz: target `go-zip` (seed 3, run 892).

**Fix.** `_zip_h1` refuses a zip whose entries do not all start at different places (`DigestError`, before anything is read).
This is the same shape as F-2 in `repo.py`, which the 0.1.8 agent owns. Test: `VerifyTests` in `test_golang.py`.
