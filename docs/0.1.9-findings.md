## F-1  safexml: an encoding expat does not know is not a `ParseError`  (fixed)

Fixed in 0.1.8 (b2bb0ff): each API raises its own parse error (`ParseError`, `ExpatError`, a fatal `SAXParseException`), saying "unknown encoding" without the document's text.

**See it.**

```python
from lazaret.safexml import ElementTree as ET
ET.fromstring(b'<?xml version="1.0" encoding="T7"?><a/>', forbid_dtd=True)      # LookupError: unknown encoding: T7
ET.fromstring(b'<?xml version="1.0" encoding="UTF32"?><a/>', forbid_dtd=True)   # ValueError: multi-byte encodings are not supported
```

Fuzz: target `xml` and `xml-minidom`, seed 0 runs 57–58 and 166 (34- and 35-byte inputs; the two above are the smallest);
`--replay` of each file. The same on 3.10 (checked on the device) and 3.13: the exception comes out of `expat`'s `Parse`,
which `safexml/ElementTree.py` (`feed`, `close`) wraps only for `expat.error`, and which minidom's `ExpatBuilder`
(`parseString`, `parseFile`) does not wrap at all. This is what the standard library's `xml.etree` and `xml.dom.minidom`
raise for these inputs too, so `safexml` is a faithful drop-in here; what is missing is the promise that makes it
*safe* to call: one exception type for hostile XML.

**Cost.** Everything that parses with `safexml` and catches only `SafeXMLError` / `ParseError` is ended by it.
`repo.pypi_latest_from_feed` is the one that does (it catches those two only, so a feed that names a bad encoding raises
`LookupError` / `ValueError` out of an install-time lookup). `repo._parse_xml` catches `ValueError` but not `LookupError`
(the `UTF32` input becomes a `FeedError`, the `T7` one does not); its watchlist caller catches `Exception`, so there it is
a skipped feed. Low: the feed is PyPI's, over TLS, and the declaration is written by PyPI. It is a hardening gap in the layer
whose job is to be the one place that turns hostile XML into one exception type.

**Fix (the owner's choice).** Either keep the stdlib's behaviour in `safexml` and say so in its docs (unsupported
encodings raise `LookupError` / `ValueError`, as the stdlib does), and make the two `repo.py` callers catch them
(`pypi_latest_from_feed`: add `LookupError, ValueError`; `_parse_xml`: add `LookupError`); or normalise in `safexml`:
`except (expat.error, LookupError, ValueError)` in `feed` / `close` and in the minidom builder, raising the `ParseError` /
`SafeXMLError` the `expat.error` branch raises, without echoing the encoding name (hostile text). The second is the
stronger one; it changes what `safexml` raises, so it belongs with the provisional-API note. Either way, add the two inputs
above to the safexml tests. When fixed, delete the four `xml` / `xml-minidom` lines of `fuzz_targets.KNOWN`; the fuzz job
then fails on a regression.

## F-2  zip entries that overlap: a warning on stderr and no anomaly  (fixed)

Fixed in 0.1.8 (b2bb0ff): `_zip_overlaps` finds them from the local headers on every version, SC-ARCHIVE-OVERLAP (MAJOR), and the warning is silenced.

**See it.** Two stored entries whose central-directory records give the same local-header offset:

```python
import io, warnings, zipfile
from lazaret.registry import repo

buf = io.BytesIO()
with zipfile.ZipFile(buf, "w", zipfile.ZIP_STORED) as zf:
    zf.writestr("a.py", b"x = 1\n")
    zf.writestr("b.py", b"y = 2\n")
data = bytearray(buf.getvalue())
first = data.find(b"PK\x01\x02")                       # the two central-directory records
second = data.find(b"PK\x01\x02", first + 4)
data[second + 42:second + 46] = data[first + 42:first + 46]     # b.py now starts where a.py does
anomalies = []
with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    print([(m[0], m[3]) for m in repo.iter_archive(bytes(data), "zip", "wheel", anomalies=anomalies)])
print(anomalies, [f"{w.category.__name__}: {w.message}" for w in caught])
# [('a.py', None), ('b.py', 'corrupt')]
# [] ["UserWarning: Overlapped entries: 'a.py' (possible zip bomb)"]
```

Fuzz: target `archive-zip`, seed 0 run 490 (911 bytes), and again in the long run (seed 12). The warning is CPython's
(3.12.3 and 3.13 on): on the device's 3.10 nothing is warned, `b.py` is `corrupt` all the same, and the anomalies list is
empty all the same, so the missing anomaly is the finding on every version and the warning is the extra on new ones.

**Cost.** Overlapping entries are the shape of a zip bomb; the reader does flag the second entry `corrupt`, but the
archive's anomalies list stays empty, so the scan does not report "this archive overlaps its entries" as a finding of its own, and
the warning goes to stderr (a line in a user's terminal, unexplained, from a hostile package). Under `-W error` (a host
that turns warnings into errors, a test runner) `UserWarning` is not one of `_ZIP_READ_ERRORS`, so it propagates out of
`iter_archive`. Low.

**Fix.** In `_iter_zip`'s `read`, run `zf.open(info)` inside `warnings.catch_warnings(record=True)` (`simplefilter("always")`),
turn an "Overlapped entries" warning into `anomalies.append(("overlap", info.filename, "entries overlap (possible zip bomb)"))`
and keep the member `corrupt`; add the snippet above as a test (skip it where `zipfile` does not warn). When fixed, delete the
`archive-zip` line of `KNOWN`.

## F-6  a zip entry with no name: `IndexError` on Python 3.10, silently skipped on 3.11+  (fixed)

Fixed in 0.1.8 (b2bb0ff): the entry is an anomaly, SC-ARCHIVE-PATH ("Unnamed archive entry"), and is not read, on every version.

**See it.** A zip with two stored entries, `a.py` and one whose name is empty (the standard library of 3.10 cannot write
such a zip, so the fixture is bytes: `NAMELESS` in `tests/architecture/test_fuzz_scripts.py::VersionBoundFindings`):

```python
from lazaret.registry import repo
from tests.architecture.test_fuzz_scripts import VersionBoundFindings
list(repo.iter_archive(VersionBoundFindings.NAMELESS, "zip", "wheel", anomalies=[]))
# Python 3.10.12: IndexError: string index out of range   (zipfile.py, ZipInfo.is_dir: self.filename[-1] == '/')
# Python 3.13.16: [('a.py', None, ...)]; the nameless entry is not read, and no anomaly says so
```

Found by the fuzzer on Python 3.10 (target `archive-zip`, seed `x1`, run 47, shrunk to 463 bytes). The 3.13 run never
sees it; the weekly job's 3.10 half does.

**Cost.** `_iter_zip` calls `info.is_dir()` before it looks at the name, and `is_dir` of 3.10 (and before) indexes the last
character. `IndexError` is not one of `_ZIP_READ_ERRORS`, so one such entry in a wheel or a zip sdist raises out of
`iter_archive`, through `_scan_artifact`, instead of becoming a finding about the archive. On 3.11+ the entry is dropped
silently (its name is canonicalised to nothing), so content in a nameless entry is neither reviewed nor reported.

**Fix.** In `_iter_zip` test the name first: `if not info.filename:` record `anomalies.append(("path", info.filename, "empty name"))`
and `continue`, before `info.is_dir()`; both Pythons then give the same answer (the member is not read, and the archive says
why). Then delete the `IndexError@repo.py` line of `KNOWN` and `test_f6_a_zip_entry_with_no_name_raises_index_error_before_python_3_11`.

## F-7  a zip entry that declares a 4 GiB LZMA dictionary: `MemoryError` where memory is capped  (fixed)

Fixed in 0.1.8 (b2bb0ff): a dictionary over 64 MiB (`MAX_LZMA_DICT`) is refused before `zipfile` sees the entry, and a `MemoryError` reading an entry leaves it unread (SC-TRUNCATED).

**See it.** `VersionBoundFindings.HUGE_DICTIONARY` in `tests/architecture/test_fuzz_scripts.py` (625 bytes: a wheel whose
entries are method 14, LZMA, and whose raw-LZMA header says `5d 00 83 ff fb`, a dictionary of 0xfbff8300 bytes). With the
address space capped, as in a container or a CI job with a memory limit:

```python
import resource, sys
resource.setrlimit(resource.RLIMIT_AS, (2 << 30, 2 << 30))
from lazaret.registry import repo
list(repo.iter_archive(HUGE_DICTIONARY, "zip", "wheel", anomalies=[]))        # MemoryError, out of `read` in `_iter_zip`
```

Without a cap, Python 3.13 on a large machine reads it (every LZMA entry `corrupt`, 27 MB peak: the dictionary is allocated
but not touched); the device's 3.10 VM raised `MemoryError` with no cap set. Fuzz: target `archive-zip`, seed 21, run 25708 (625
bytes), on the device. `zipfile`'s `_LZMADecompressor` builds `lzma.LZMADecompressor(FORMAT_RAW, filters=[…])` on the first
read of the entry, and the allocation is asked for before a byte of the entry is decoded.

**Cost.** `MemoryError` is not in `_ZIP_READ_ERRORS`, so it leaves `iter_archive` (and `_scan_artifact`): one 625-byte wheel
ends the review of a package on any host whose memory is limited, where a hostile package should end as a finding. On a host with
no limit the process asks the kernel for 4 GiB of address space per entry and gets it (nothing is touched), so it is the
capped hosts that fail, and they are the ones that cannot spare the memory for a second try.

**Fix.** Either, or both: add `MemoryError` to `_ZIP_READ_ERRORS` so the entry is `corrupt` with a detail; and refuse an
LZMA entry before decoding it. Wheels may use stored or deflated entries only (PEP 427), so a method-14 entry in a wheel is
already an anomaly worth reporting; for a zip sdist, read the 9 bytes after the local header (version, length of the
properties, the 5 property bytes) and refuse a dictionary over some bound (64 MiB is generous). When fixed, delete the `MemoryError@repo.py` line of `KNOWN` and
`test_f7_a_huge_lzma_dictionary_is_a_memory_error_where_memory_is_capped`.

## F-3  sca: an include with a NUL byte in a requirements file  (fixed)

**See it (before the fix).** A `requirements.txt` of `-r\x00` made `os.path.realpath` raise `ValueError: embedded null byte`
inside the include reader, and with it `scan_all`, so one hostile file ended the whole inventory. Fuzz: target
`sca-requirements-txt`, seed 0 run 8, three bytes (`-r` NUL).

**Fix.** `_scan_requirements` treats an include path with a NUL as "not found" (counted in the existing
`requirements includes not found` warning) before it reaches `realpath`; the rest of the file and the other includes are read.
Tests: `tests/scanner/test_sca_fuzz_findings.py::NulInAnInclude`.

## F-4  sca: a deeply nested TOML file raised `RecursionError`  (fixed)

**See it (before the fix).** `x = [[[[…` (or `[[[[…`, or inline tables in inline tables) a few hundred levels deep:
`tomllib` (3.11+) raises `RecursionError`, which `sca.load_toml` did not turn into the `ValueError` its callers catch.
Callers hit: `scan_all` for `uv.lock`, `poetry.lock`, `pylock.toml` and `pyproject.toml`, the guard's `uv_lock_packages`,

**Fix.** `load_toml` maps `RecursionError` to `ValueError("TOML: RecursionError")`. Tests: `DeepToml` in the same test file
(each reader warns `unparseable <name> file(s)` and goes on; the guard's reader returns no packages).

## F-5  sca: `setup.py` with an invalid escape printed a `SyntaxWarning`  (fixed)

**See it (before the fix).** `setup.py` text such as `install_requires=['a\d==1']` (a docstring of `\d+` does the same):
the reader compiles the file to read its literals (it never runs it), and Python 3.12+ prints
`SyntaxWarning: invalid escape sequence '\d'` on stderr; under `-W error` the compile raised and the file was read by its tokens
instead (the same answer for these inputs, by another path). Fuzz: target `sca-setup-py`.

**Fix.** `_setup_py_requirements` parses inside `warnings.catch_warnings()` with `simplefilter("ignore")`, and leaves the
caller's filters as they were. Tests: `SetupPyWarnings`.

## F-8  registry modules: an error message that quotes odd characters was over 1,200 characters  (fixed)

**See it (before the fix).** `Crates().check_version("\udcff" * 500)` or `Go().check_version("\U0010ffff" * 500)` raised a `SpecError`
whose message held `repr(text[:120])`: every such character is escaped to 6 to 10 characters, so the message was 720 to 1,200

**See it (before the fix).** A module zip in which two central-directory entries have one local header offset: `zipfile` of

## F-10  npm tarballs: entries npm's tar reader reads differently from the registry's  (fixed)

**See it (before the fix).** npm unpacks a package with node-tar (pacote: the first path part stripped, links dropped); the
registry read the tarball with Python's tarfile alone. The differential target `archive-npm-diff` (BR-4), which runs npm's
own node-tar beside the reader on the same bytes, found tarballs from which npm writes what the scan did not read:

- a ustar prefix field whose first byte is NUL and whose 131st is not: node-tar prepends the prefix whenever byte 475 of
  the header is not NUL, even when it reads empty, so `index.js` is `/index.js`, which npm writes as `index.js`; tarfile
  reads `index.js`, a top-level file, which the registry drops as npm's strip leaves nothing of it. The package's main
  file was never read (seed 1, the first run);
- a pax global header's `path`: tarfile gives it to every later entry, node-tar to none, so npm writes package.json and
  index.js where the scan read two files named `global.js`;
- a regular file whose name ends in `/`: a directory to node-tar (its size taken as 0), which reads the file's data as
  the next headers, so a tar entry inside the file is what npm writes;
- a file's header that has a link name: node-tar skips the header ("linkpath forbidden") and reads its data as headers;
- a pax record whose value holds a newline (node-tar parses pax line by line, so the record is dropped and the ustar
  name stands), an `N` or `X` header (node-tar applies them; tarfile does not know them), a name whose bytes are not
  UTF-8 (U+FFFD in node-tar, a surrogate escape in tarfile, so a `main` names a file the scan read under another name),
  a NUL before a newline in a name (node-tar's `/\0.*/` stops at the line terminator; tarfile stops at the NUL);
- roots: node-tar takes them off by Windows' rules on every platform, so `package/C:index.js` is index.js to npm
  everywhere (the registry kept `C:`), and `package/\\srv\sh\index.js` is index.js to npm on Linux and macOS and
  srv/sh/index.js to npm on Windows and the registry.

**Fix.** `registry/npmtar.py` models node-tar 7.5's reading (the version npm 10 and 11 bundle), JavaScript's semantics
included, and `_iter_tar` feeds it the stream tarfile reads: an entry npm writes that tarfile read at another place, under
another path or not at all, a header node-tar finds invalid, or a size it would read by JavaScript's arithmetic, makes the
archive corrupt (INCOMPLETE, so the guard refuses it); a drive-relative root is taken off as node-tar does. The target
holds the model to npm's node-tar too (what it says npm writes is what npm writes). Tests:
`tests/registry/test_npm_tar_readers.py` (each case, with npm's node-tar run on it where node is here),
`test_fuzz_scripts.py` (`archive-npm-diff`'s promises). Left: pip's reading of an sdist on the Python that installs it
(3.10 to 3.14 read headers differently too), cargo's, VS Code's zip reader (BR-4's next part).

## F-11  sdists and wheels: members pip writes elsewhere than the scan read them  (fixed)

**See it (before the fix).** pip unpacks an sdist with its own code before it builds it (pip/_internal/utils/unpacking.py)
and installs each of a wheel's files at its path's normpath. The differential target `archive-pip-diff` (BR-4), which runs
pip's own unpacking beside the reader on the same bytes, with pip 24.0 (Python 3.10, 3.11 and 3.13) and 24.3.1 (3.12), and
a reading of pip's wheel installer, found:

- a member whose path goes through `..` and stays in the folder. tarfile writes `pkg-1.0/x/../setup.py` through the path,
  as setup.py, over the setup.py before it: pip 24.0 does always, and pip 24.3.1 once `x/` exists. pip's wheel installer
  writes `x/../evil.pth` as `evil.pth`, a .pth file at the top of site-packages. The registry refused such a member as
  an unsafe path (SC-ARCHIVE-PATH, MAJOR) and never read it: a release whose setup.py, or whose .pth file, came in
  through `..` was WARN, which the guard installs (each shown with each pip here; nothing was run);
- an sdist whose members do not all sit in one top folder. pip takes the top folder off only when every member, folders
  too, has the same one (`has_leading_dir`), and otherwise writes each member under its whole name; the registry took
  the first folder off every name, so a module setup.py imports was read where pip does not write it. An sdist whose
  names all start with `./` likewise (pip takes only the `.` off);
- a member named with a leading slash: pip 24.0 refuses the archive, and pip from 24.1 writes the member (its tarfile
  filter takes the slash off) where the registry reads it.

**Fix.** A wheel's or an sdist's member whose `..` stays in the folder is read where pip writes it, with an
SC-ARCHIVE-PATH of its own ("Archive path through '..'", MAJOR), and the file's own tests apply there: the setup.py and
the .pth file above are SUSPICIOUS. One that leaves the folder is refused as before (pip refuses the archive). An sdist
whose members pip places otherwise than the registry reads them is corrupt (`_pip_sdist_disagreement`, with pip's
has_leading_dir and split_leading_dir written out): INCOMPLETE, so the guard refuses it. node-tar, cargo's tar, Go and
VS Code's yauzl refuse a `..`, and the registry still does for them. Tests: `tests/registry/test_pip_archive_paths.py`
(each case, with pip's own code run on it where pip is importable), `test_fuzz_scripts.py` (`archive-pip-diff`'s
promises). Left: cargo's tar crate, yauzl and Go's archive/zip against their own readers, then the headers in Rust
(BR-4's next part).

## F-12  the JavaScript parser refused Annex B's HTML-like comments, so a file that opened with one lost its tree  (fixed)

**See it (before the fix).** The supply-chain tests read a package's JavaScript on the engine's tree where `js_parse`
(`jsparse/parser.rs`) reads the file, and on its text where it does not (`signs.rs`'s `local_data_sent` and
`received_code`, `scanfile.rs`'s `tree_decode_flow`: the text followers answer then). Annex B's HTML-like comments
(ECMA-262 B.1.1), which V8 reads in a script — Node's CommonJS: a `.cjs`, and a `.js` whose package.json does not say
`"type": "module"` — were syntax errors to the parser:

- `<!--` opens a line comment anywhere a token may begin: a file that opened with `<!-- a banner` did not parse
  ("unexpected character '!'");
- `-->` opens one where a line begins (the input's start, or after only blanks and comments since a line terminator; a
  block comment that holds one opens the line too): `0;\n--> a note\nx = 1;` did not parse.

Such a file was not unread: the text followers answered for it, as for any file the parser refuses. It lost what only the
tree answers — another package's code rewritten (D-9), a program a dropper carves out of another file, the loads D-13
compares with package.json (`repo._dev_only_loads` skips a module the engine cannot read), the cross-file pass in project
mode (a Q-FLOW-SKIPPED note) — and the tree's precision where its answer stands in for the text followers'. Found by a
hand-written probe of constructs a package's script uses, checked against V8 (`scripts/fuzz/js_v8_compile.cjs`: V8
compiles each source as a script and as a module, nothing run), while X-1's `js-parse` target was written.

**Fix.** In JavaScript, `skip()` (the parser's reading of blanks and comments between tokens) takes `<!--` as a line
comment wherever a token may begin and `-->` as one at a line's start (the input's, by `pos == 0`; otherwise after a line
terminator in the run), as V8 reads a script. V8 refuses a module that holds either ("HTML comments are not allowed in
modules"), even `x <!--y`, which the standard reads in a module as `x < !--y`; Bun 1.3 refuses `<!--` everywhere and takes
a line's `-->` for a comment, in a module too. So nothing a runtime runs is taken for a comment in a JavaScript file.

TypeScript is another matter: tsc has no HTML-like comments. tsc 6.0.3 compiles `z = 5 <!--y, f()` to
`z = 5 < !--y, f();`, which calls `f` (so does `z = 5` with `<!--y, f()` on the next line), and reports a syntax error
for a file that opens with `<!--`; tsx (esbuild) and Node's type stripping read a comment. In the TypeScript dialect `<!--` stays `<` `!` `--`,
as tsc reads it (a first version of this fix, never applied, read a comment there too). The supply-chain facts read a
TypeScript file's text as JavaScript first (`jsflow::supply::facts`), so the tree says when its JavaScript reading took a
`<!--` after a token for a comment (`Tree::html_after_code`), and the facts then read the text as tsc reads `<!--`
(`jsparse::parse_with`), which sees the code the comment hides; where that reading does not parse, no runtime runs it so,
and the comment's reading stands. A `<!--` before the first token is a comment in every reading that runs the file. `-->`
where a line begins is never code (there `--` is a prefix operator, and `>` begins no operand), so it is a comment in
either dialect. The exact bytes only: `a < !b` and `a-->b` (a postfix `--` and `>`) are untouched. The layout lexer
(`lex/js.rs`), whose tokens the text followers read, reads both as code and is unchanged.

Tests: `jsparse/tests.rs` (`annex_b_html_comments_are_comments_in_javascript`,
`typescript_reads_html_like_open_comments_as_tsc_does`, `an_html_like_open_comment_after_code_is_marked`),
`jsflow/supply.rs` (`html_like_comments_are_read_as_the_runtimes_read_them`), `tests/architecture/test_jsparse_v8.py`
(V8 on a curated list, which this fix added). Rule set unchanged (a parser fix, no rule).

**Left.** The parser is stricter than V8 in other places, and a file Node runs that it refuses loses the tree-only
answers above the same way: an assignment or update to a call (`if (0) { f() = 1; }`, which V8 leaves to a runtime
error), `for (let in x)` in sloppy code, and nesting past the parser's bounds (126 parentheses or arrays, 84 objects, 256
blocks). The backlog's JS-PARSE-STRICT.

## F-13  `lazaret-sca --update-bundle` failed over the native transport: an OSV export's budget was past what it carries  (fixed)

**See it (before the fix).** Found by the live checks (Oct 9: `specs/lazaret-0.1.9-live-checks-2026-10-09.md`, item 8), on
a Mac with the native library: `python3 -m lazaret.scanner.sca --update-bundle --bundle B` printed `error: cannot fetch
https://storage.googleapis.com/osv-vulnerabilities/npm/all.zip: a budget of more than 2147483648 bytes` and left the bundle
as it was. The SCA's feeds have gone over the native transport since NET-1's second part (`sca_feeds._fetch_native`), each
with its own byte budget. An OSV export's, `MAX_OSV_ZIP_BYTES`, was 4 GiB (from 0.1.7), and lazaret-net refuses a request
whose budget is past its `MAX_BODY`, 2 GiB, before it connects; its comment still said the Python side's largest budget was
500 MB. So every update failed wherever the native library is (decision 12), unless `LAZARET_NETWORK=python`. The tests
read the feeds from local files, the way a mirror is read, and never through the native transport with these budgets; the
test of the real feeds (`LiveFeedsTests`, with `LAZARET_TEST_FEEDS=1`) does not run in the sandbox, which cannot reach
them.

**Fix.** An OSV export's budget is the most the native transport carries, `nativenet.MAX_BODY` (2 GiB: the Python side's
copy of lazaret-net's, which a test holds to it). On Oct 9 the exports were well within it: npm's, the largest, was 208 MiB (230,260 records), PyPI's 34 MiB, Go's 12 and crates.io's 3.4. A request whose budget is past `MAX_BODY` now goes to
urllib (`nativenet.UsePython`, as one through a proxy the native client does not take does) rather than failing: only a
setting asks for one now (`LAZARET_MAX_DOWNLOAD_BYTES` or `--max-download-bytes` past 2 GiB, which failed the same way).
The guard's stream limit is the same constant. Tests: `test_sca_feeds`'s `NativeFetchTests` (each feed's budget, over the
native transport, against a local HTTPS server: the OSV one failed as above before the fix) and its check that each
feed's budget is within `MAX_BODY`; `test_nativenet` (the constant is lazaret-net's; a budget past it goes to urllib, one
at it is carried).
