# Lazaret

Static security & quality analysis for Python, JavaScript, and SQL — a lightweight toolkit. No dependencies at all: it runs on the Python standard library and its own native engine (Rust, no external crates), or in any browser, and even building it downloads nothing.

## Install

```bash
pip install lazaret          # from PyPI: one package, zero dependencies
```

Lazaret's scanning engine is native code (written in Rust, with no external crates). On Linux (x86-64 and ARM64, glibc 2.28 or later), macOS (Apple silicon, and Intel from 10.12) and Windows (x64), pip installs a platform wheel that carries it; everywhere else pip builds a wheel from the source distribution, which compiles the engine and so needs Rust (`rustup`; about a minute). See *Dependencies & licensing*.

This gives five commands: `lazaret` (project scanner, and `lazaret guard`, which checks what npm, pnpm, yarn, Bun, pip, uv, go, cargo or a VS Code editor is about to install before it runs), `lazaret-registry` (npm, PyPI, Go module and crate auditing), `lazaret-mcp` (MCP server), `lazaret-sca` (dependency CVE matching) and `lazaret-guard` (`lazaret guard` under its own name). Each also runs as a module, e.g. `python -m lazaret`, and prints its version with `--version`; if `lazaret guard` answers with the scanner's usage, an older `lazaret` is earlier on your PATH (`which -a lazaret`).

On a machine with Node but no Python, the project scanner is also on npm, with the same rules and zero dependencies (its rules run in Lazaret's native engine, compiled to WebAssembly and shipped in the package):

```bash
npx lazaret check .          # or: npx lazaret .   (or: npm install -g lazaret)
```

The npm package is the project scanner only; registry auditing, the install guard, custom taint specs, SCA and the MCP server come with the Python package. Its cross-file taint passes (`X-*` findings) are the native engine's, for JavaScript and for Python, as in the Python package. The npm CLI takes the same flags as the Python one (`--deps`, `--exclude`, `--out-dir`, `--html`/`--json`, `--sarif`, `--baseline`, `--ci`, `--force-overwrite`, `--no-redact-secrets`, `--verify-secrets`, `--max-source-bytes`, `-q`) and rejects unknown ones. The two packages are tested to agree exactly — every finding including its severity and message, the metrics, ratings, quality gate and exit code (`tests/architecture/test_js_parity.py`, which also runs an adversarial fixture set). Since 0.1.8 the npm package's rules, supply-chain tests and cross-file received-code follower (a `--deps` value received in one file of a package and run in another) are the native engine's, the one the Python package's wheels carry (`docs/RUST_ENGINE.md`), and the npm CLI spreads a large scan over worker threads (`LAZARET_THREADS`) with the same report. The browser dashboard carries a port of the same engine and is held to the same findings (`tests/scanner/test_review_dashboard_parity.py`).

From a checkout, `pip install ./python` (or `pip install -e ./python` for development) works with no network access: Lazaret builds with its own standard-library build backend, which compiles the engine with your Rust toolchain (the workspace has no external crates, so cargo fetches nothing).

## Components

| Module / command | What it is |
|---|---|
| `lazaret` (`lazaret.scanner.core`) | CLI: scan a directory tree, or a GitHub or GitLab repository at a commit, and produce project reports |
| `lazaret.scanner.flow` | Interprocedural / cross-file taint engine (used by the CLI, MCP, registry) |
| `lazaret.scanner.engine`, `rust/` | The scanning engine (Rust, no crates): the supply-chain tests, the per-file rules, the cross-file follower |
| `lazaret-sca` (`lazaret.scanner.sca`) | Dependency CVE scanner: matches the npm, PyPI, Go and Rust packages a project installs or pins against a CVE bundle |
| `lazaret-registry` (`lazaret.registry`) | Registry scanner: audit npm and PyPI packages, Go modules and crates, track state in a DB |
| `lazaret guard`, `lazaret-guard` (`lazaret.registry.guard`) | Install guard: check what npm, pnpm, yarn, Bun, pip, uv, go, cargo or VS Code (and the editors built on it) is about to install (resolve, fetch, scan in memory) and block it before it runs |
| `lazaret hook` (`lazaret.scanner.hook`) | Commit-time gate: credentials, vulnerabilities and supply-chain threats in the files being committed, as staged; a pre-commit hook |
| `lazaret-mcp` (`lazaret.mcp`) | MCP server: lets Claude scan code and changes via tools |
| `lazaret/web/lazaret.html` | Web dashboard: paste or upload code, scan in the browser |
| `lazaret.pg` | PostgreSQL client used for the registry state DB (pure stdlib) |
| `lazaret.safexml` | Safe XML parsing (a defusedxml-style layer over the stdlib) |
| `examples/` | Taint-spec template and MCP client configuration template |

## Scanning a project

```bash
lazaret <directory>                 # scan + write lazaret-report.{html,json} under the scan root
lazaret . --html out.html           # custom report path (relative paths: under the scan root)
lazaret . --out-dir /tmp/cg-reports # write reports elsewhere (must exist and be writable)
lazaret . --exclude fixtures -q     # skip extra dirs, summary only
lazaret . --ci                      # exit 1 if quality gate fails (for CI)
lazaret . --deps                    # also audit node_modules/venv for supply-chain indicators
lazaret . --max-source-bytes 32000000  # read larger source files (default 16,000,000)
lazaret . --sarif out.sarif         # SARIF 2.1.0 for GitHub code scanning
lazaret . --baseline prev.json      # mark issues not in a previous report as new
lazaret . --no-redact-secrets       # keep credential lines in reports (default: redacted)
lazaret . --verify-secrets          # ask each secret's provider whether it is live (off by default)
lazaret . --taint-config taint.json # extend the taint model (see "Custom taint config")
lazaret scan github:owner/repo@v1.2.3  # a repository at a commit (also gitlab:group/project@ref)
lazaret extension.vsix                # a VS Code extension's package
lazaret --extensions                  # the extensions VS Code, Cursor, VSCodium… have installed
```

**Secret redaction (on by default):** credentials are replaced with a
placeholder *before* they reach any artifact — terminal, JSON/HTML/SARIF
report, and the registry state DB — so scanning your own code doesn't copy
real credentials into CI artifacts (audit L1). That covers the flagged line of
a credential finding (S-SECRET, S-TOKEN, SQL-CRED, S-ENTROPY) and every
*context* line shown with any finding: whole PEM private-key blocks (BEGIN
through END), the file's entropy-flagged literals wherever they appear, URL
userinfo, the provider token formats S-TOKEN knows (GitHub's
`ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`/`github_pat_`, npm's `npm_`, OpenAI's and
Anthropic's keys, and the others), and SQL `IDENTIFIED BY` / `PASSWORD` in any
letter case. Finding messages and the install-hook `cmd` field are redacted
the same way. Baselines keep matching because the placeholder is deterministic
for a given rule + secret. Pass `--no-redact-secrets` when you are auditing a
leak and need the exact bytes in the report. It applies to project scans only:
registry results are always redacted, because they are stored (see *Registry
scanning*).

**Live secrets (`--verify-secrets`, off by default):** after the scan, each
secret finding is asked about where a provider can say whether it is live: a
GitHub, Slack, Stripe or npm token, an OpenAI or Anthropic API key (not an
admin key or an OAuth token: those are detected, not asked about), or an AWS
key pair (a key id and a secret key in the same file). Each credential goes to
its own provider alone, over HTTPS, in a call that only authenticates
(GitHub's `GET /user`, Slack's `auth.test`, AWS STS's `GetCallerIdentity`…),
never following a redirect; before the first call a note on stderr says which
providers will be asked and where each credential goes. A finding then says
what its provider said: **live** (a BLOCKER, with the account the provider
names: revoke it now), **rejected** (kept: revoke it anyway, the history keeps
it) or **unknown** (kept, and why: no answer in time, a rate limit…); the JSON
report's `verification` and each finding's `verified` say the same, and SARIF
carries `verified` in a result's properties. A Google API key, a JWT, a
private key or a database's password has no provider to ask; the report counts
those. The value itself is never written anywhere: it is read again from the
file, in memory, for the call. The flag works for any target, a `github:` or
`gitlab:` repository too; the guard, the registry auditor, the MCP server and
the pre-commit hook never verify. The npm package's `--verify-secrets` asks
the same way (Node's `https`, TLS 1.2 at least, `HTTPS_PROXY` through an
http:// proxy's tunnel) and reports the same.

**Baselines:** a baseline must be a report this engine wrote, and a hostile
repo must not be able to supply one (audit G17), because a hand-crafted
"previous report" would hide its findings as "not new". The engine marker
alone is public, so it is not trust:

- With `LAZARET_BASELINE_KEY` set, JSON reports carry an HMAC-SHA256
  `baselineSignature` over their finding fingerprints, and a baseline is
  trusted only if its signature verifies with that key.
- Without a key, a baseline stored *inside* the scanned tree is untrusted —
  keep it outside (e.g. `$RUNNER_TEMP`). One outside the tree is trusted if it
  carries the engine marker.

An untrusted baseline counts every finding as new (a warning says why).

**Where reports go, and why a scan never ends in a lost result:** report files are written under the
directory you scanned (or the directory you pass to `--out-dir`), never the current working directory —
so read-only CI checkouts and containers don't pay for a full scan and then fail to save it. The CLI
checks that every report destination is writable *before* scanning begins (exit code `3`, with a clear
message, if not). Pre-existing files at a report path are never silently overwritten: Lazaret re-writes
its *own* earlier reports (that's the re-scan workflow; any report size) but refuses to replace a file it
didn't produce — use `--force-overwrite` to override that explicitly. Directory, symlink and special-file
destinations are always refused, even with `--force-overwrite`, and so are two reports resolving to one file
(`--sarif lazaret-report.json` next to the default JSON report). Writes are atomic (temp file + rename), so
an interrupted run leaves the previous report intact, and a re-scan keeps the existing report's file
permissions.

**Exit codes:** `0` scan ok (gate passed, or no `--ci`); `1` gate failed with `--ci` — and, without
`--ci`, only for SC-MANIFEST-DEPTH (a manifest built to crash scanners); `2` usage error (unknown option,
missing, non-directory, unreadable or empty target); `3` report output error; `4` taint-config rules
rejected (see "Custom taint config"); `5` internal error (`error: internal: …`; set `LAZARET_DEBUG=1` for
the traceback). A crash never looks like a failed gate.

**A repository at a commit (`github:`, `gitlab:`).** `lazaret scan github:owner/repo[@ref]` or
`gitlab:group[/subgroup…]/project[@ref]` (the word `scan` is optional) resolves the ref (a branch, a tag
or a commit; none means the default branch) to a commit, reads that commit's archive into a temporary
directory, scans it with the options you give (every option of a folder's scan works), and removes the
directory. The `Source:` line and the report name the commit, so a branch that moves while the scan runs
cannot change what was read: the report's `project` is `github:owner/repo@<sha>`, its `source` block has
the repository, the ref you asked for, the commit, the files and bytes read and what was not read, and a
SARIF report maps its root to the repository at that commit (`versionControlProvenance`). The report
files are named for the commit (`lazaret-github-owner-repo-0123456-report.json`) and written to the
current directory unless `--out-dir`, `--json`, `--html` or `--sarif` say otherwise; the destination is
checked before anything is fetched. Paths the archive leaves out (`export-ignore` in `.gitattributes`,
where many repositories keep their tests and `.github/`) are fetched one by one (from
raw.githubusercontent.com for a public GitHub repository, through the API with a token or on GitLab),
and each is written only if it is the blob the commit's tree names. A commit that was not read whole (a
path that could not be fetched within the budget, a tree too large to list, an archive that hit a
limit) is said after the report and makes the result `incomplete`; with `--ci` the exit status is then
1 even when the gate passed, unless you pass `--accept-incomplete`. Submodules are named, not read.
`GITHUB_TOKEN` and `GITLAB_TOKEN` (read-only; for private repositories and GitHub's rate limit) are read
from the environment and sent to the API host only; `LAZARET_GITLAB_URL` names a GitLab instance other
than gitlab.com (https only). Nothing in the repository is run. A ref that cannot be resolved or a
repository that cannot be fetched is exit 2. The npm package has no `github:` form.

**VS Code extensions (`.vsix`, `--extensions`).** `lazaret FILE.vsix` scans an extension's package, and
`lazaret --extensions` the extensions installed for VS Code, VS Code Insiders, VSCodium, Cursor, Windsurf,
Kiro, Positron and code-server, and on a remote host for the VS Code and Cursor servers (each keeps them in
`~/<its folder>/extensions`; the folder `VSCODE_EXTENSIONS` names is read too). `lazaret --extensions PATH …`
scans the extension folders, extensions folders and `.vsix` files you name. An extension runs in the
editor's extension host with all of your access, so it is read as `lazaret-registry` reads an npm package
(see *Registry scanning*), with the editor's rules for what runs: its `main` and `browser` modules and what
they load run when the editor activates it (at every start for the activation events `*` and
`onStartupFinished`, which the result says) and get the import-time test; so does the code its contributions
name, which runs without them, and the finding says when: a TypeScript server plugin
(`typescriptServerPlugins`, loaded by the TypeScript server whenever a JavaScript or TypeScript file is open,
the extension activated or not), a debug adapter's program (`debuggers`, started with a debug session), a
notebook renderer and a Markdown preview script (in a webview); the rest of its code gets the use-time test;
and `vscode:uninstall`, the one script VS Code runs (`node` and a file, once the extension
has been uninstalled), gets the install-hook test. npm's scripts, a bundled package's scripts and a
`binding.gyp` never run, so they are not hooks. The result lists the extensions it brings
(`extensionDependencies`, `extensionPack`), and an identifier, its own or one it brings, like a most-installed
extension's of another publisher is SC-TYPOSQUAT (see *Registry scanning*). An installed extension is read as
its `.vsix` would be, and a link out of its folder is not followed (the verdict is INCOMPLETE). Each
extension gets a registry verdict (OK, WARN, INCOMPLETE or SUSPICIOUS); `--ci` exits 1 when one is
SUSPICIOUS or INCOMPLETE, `--json PATH` writes them all (under the report rules above), and `--quiet` prints
only those that are not OK. Nothing is run. The npm package has no extension scan yet.

**What gets scanned:** `.py .pyw .js .jsx .ts .tsx .mts .cts .mjs .cjs .sql` sources (a `.ts`/`.mts` that is an MPEG transport stream is video, not TypeScript), `.go` and `.rs` sources (since 0.1.9, a project's own: hardcoded credentials (S-SECRET reads `name = "…"` and `name: "…"`, Go's `name := "…"` and `var name string = "…"`, and Rust's `const`/`static NAME: &str = "…"`, byte and raw literals included), token formats (S-TOKEN), Trojan Source characters (S-BIDI), TODO markers, and the obfuscation and encoding checks every text gets — hex-escaped text, invisible characters, base64 blobs, high-entropy literals — with comments and strings read as Go and Rust read them; their lines count in the metrics but not in the duplication; a package's are read with the engine's Go and Rust readers, and so is a Go or `cargo vendor` tree with `--deps`, below), scripts whose `#!` line names
Node (or bun, deno, ts-node, tsx) or Python, whatever their name (`bin/cli`, a hook's `./setup`), `package.json`, `binding.gyp`
and every other `.gyp`/`.gypi` file (install hooks), `.pth` files (their `import` lines run at every Python start: SC-PTH-EXEC), config and data files for credentials (see Secrets below) — and editor and AI-agent settings for the commands they run, GitHub Actions workflows for the shapes the Shai-Hulud worms planted (see Persistence targets) — and every other regular file by magic bytes (executables, shared objects, nested
archives, opaque blobs — see Binary artifacts). `.git` is always skipped. `node_modules`,
`bower_components` and `site-packages` are pruned unless `--deps`; `vendor`, `venv`, `.venv` and `env`
are pruned only when they look like dependency trees (a `pyvenv.cfg`, `modules.txt`, `autoload.php`,
`package.json` or `*.dist-info`/`*.egg-info` directly inside, or for `vendor` since 0.1.9 a crate directory
with `cargo vendor`'s `.cargo-checksum.json`) — otherwise they are first-party code and
scanned. With `--deps`, a Go `vendor/` and a `cargo vendor` tree are read as the registry reads a module zip and
a `.crate` (since 0.1.9): the file rules on each `.go` and `.rs` file a build compiles (not `*_test.go`,
`testdata/`, a crate's `tests/`, `benches/`, `examples/`), and the engine's Go and Rust readers on each module
`vendor/modules.txt` lists and each crate, its `Cargo.toml` read for the build script and the library: what a
Go package's `init` code reaches is SC-IMPORT-RISK, a build script or a procedural macro SC-INSTALL-HOOK
(CRITICAL), the strong reasons of the rest SC-USE-RISK. `dist/`, `build/` and `migrations/` are scanned. `__pycache__` is not scanned as source, but every
`.pyc` in it is checked: an unchecked-hash pyc (PEP 552; Python runs it without looking at the source) is
SC-PYC-UNCHECKED (CRITICAL), and one with no matching source is SC-PYC-ORPHAN (MAJOR). Every pruned tree
is listed as a Q-SKIPPED-TREE note, so the coverage gap is visible.

Only regular files are opened: symbolic links are never followed (Q-SYMLINK note — a link can't pull a
file from outside the repo into your report), FIFOs, sockets and unreadable entries become Q-UNREADABLE
notes instead of hanging or aborting the scan, and the walk is iterative (no recursion limit on deep
trees). Source files and manifests over 16,000,000 bytes get SC-TRUNCATED instead of a silent skip
(`--max-source-bytes` or `LAZARET_MAX_SOURCE_BYTES` changes the limit, for the MCP server and the
registry scanner too; the browser dashboard keeps 2,000,000); other large files are classified from
a header sample. Bundles in `node_modules` fit: typescript's `lib/typescript.js` is 9.1 MB and scans in
a few seconds. A source file's scan is bounded by the engine's work budget, not by a clock, so a file gets
the same findings on every machine (SC-TRUNCATED "reading it spent the engine's work budget" if it is ever
hit — a backstop; the rules are linear-time); a config or data file's scan has a 30-second time budget
(SC-TRUNCATED "scan time budget exceeded"). A file whose scan fails with an internal error is SC-TRUNCATED
too ("its scan failed"): the rest is still scanned and reported, and the gate fails. A `binding.gyp` lists
at most 100 install-hook findings (one more sums up the rest, at their highest severity) and is SC-TRUNCATED
past 100,000 values or 2,000,000 characters of commands.

**Encodings:** a BOM decides first (UTF-8, UTF-16 LE/BE); a NUL in the first four bytes is read as
BOM-less UTF-16 only when the result is text (otherwise `/*\0*/eval(…)` would hide as UTF-16 garbage);
Python files honor PEP 263 coding cookies as the interpreter does: single-byte codecs with Python's own
tables, UTF-7, the escape codecs and the common multi-byte ones, the same in every engine. Anything that
isn't plain UTF-8 gets a Q-ENCODING note and is scanned as decoded; a codec Lazaret can't decode exactly as
Python does (UTF-32, ISO-2022-KR, a `\N{name}` escape under unicode_escape, …) is read as UTF-8 and is
SC-TRUNCATED, so the file is never passed as fully scanned; so is a source file whose bytes don't decode to
text at all (more than 30% invalid bytes or control characters), as in the registry. A UTF-7 cookie is SC-UTF7 (CRITICAL) and a
unicode_escape or raw_unicode_escape cookie is SC-ESCAPE-CODEC (CRITICAL): Python decodes `+AAo-` or
`\x0a` to a newline before it reads the code, so text every editor shows as a comment can be code.

File names and scanned text printed to the terminal are sanitized: C0 controls (except tab/newline), DEL,
C1 controls (U+0080–U+009F) and bidi controls are shown as `·`, so a hostile file name can't rewrite your
terminal.

### In CI

This repository is a GitHub Action (`action.yml`). It installs Lazaret from the commit you pin it to,
compiling the engine with the runner's cargo (a minute or two; GitHub's hosted runners have Rust), so what
runs is that commit's code rather than a package fetched by its version number. It scans the workspace
with `--ci` and writes a SARIF report for code scanning, whose path is its `sarif` output:

```yaml
jobs:
  lazaret:
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      security-events: write        # for the SARIF upload
    steps:
      - uses: actions/checkout@<full commit SHA>      # pin every action to a commit: a tag can be moved
        with:
          persist-credentials: false
      - uses: lazaret-dev/lazaret@<full commit SHA>   # a release tag's commit
        id: lazaret
      - uses: github/codeql-action/upload-sarif@<full commit SHA>
        if: ${{ !cancelled() }}     # upload when the gate fails too
        with:
          sarif_file: ${{ steps.lazaret.outputs.sarif }}
```

Inputs: `path` (the directory to scan, default `.`), `sarif` (default `lazaret.sarif`, under the scanned
directory), `gate` (`true`, the default: the step fails when the quality gate does; the report is written
either way) and `deps` (`true`: also audit installed dependencies, `--deps`). In other CI systems, or to
skip the compile, install a platform wheel (`pip install --only-binary :all: lazaret==X.Y.Z`; a
requirements file with `--hash` lines pins the files too) and run `lazaret . --ci --sarif lazaret.sarif`.

A project scan checks your workflows offline (see "CI files' hardening" under Detection capabilities).
What their `uses:` lines point to can be checked online too: `python -m lazaret.registry.actions
.github/workflows/*.yml` asks GitHub about each action once and reports a pin that is in no branch and
at no tag of its repository, such as a fork's commit GitHub serves under the parent's name
(SC-ACTION-IMPOSTOR, CRITICAL when every branch and tag was compared); a version tag that points to
another commit than when it was first seen (SC-ACTION-TAG-MOVED, CRITICAL; what was seen is kept in
`~/.cache/lazaret/actions-pins.json`, `--pins FILE`, until `--accept-moved`); a tag whose commit is on
none of the branches compared (SC-ACTION-OFF-BRANCH); `@<sha> # v1.2.3` where the tag names another
commit (SC-ACTION-PIN-MISMATCH); and, in the action's own `action.yml`, a Docker image without a digest
(SC-ACTION-DOCKER-UNPINNED; MINOR for one of Docker's official images at a version tag) or a composite
action's steps that are not pinned, followed two levels deep (SC-ACTION-NESTED-UNPINNED). It then reads
each action's own code at the commit its `uses:` resolves to, the archive the runner fetches, as the
runner runs it: a JavaScript action's `pre`, `main` and `post` scripts and the modules they load by the
import-time test (SC-IMPORT-RISK); a composite action's `run:` steps as install hooks are read, with the
action's own scripts they run (a path built from `github.action_path`; a step's other paths are the
workspace's) and their shell, Python or PowerShell (SC-INSTALL-HOOK); a Docker action's Dockerfile, its
base images (SC-ACTION-DOCKER-UNPINNED) and the script its entrypoint runs; and the rest of the
repository by the use-time test (SC-USE-RISK). In an action, what CI code does as its job (a named
token sent to its service, a file uploaded, a package published) is not counted, a script fetched and
run as it arrives (`curl … | sh`) is MAJOR, as it is in a workflow, and a stealer's or a backdoor's shape
(the whole environment sent, a decoded script written and run, a reverse shell) is CRITICAL. `--no-code`
skips it. It prints JSON and exits 1 for a finding, 3 when something could not be checked (GitHub allows
60 requests an hour without `GITHUB_TOKEN`; a private repository; an expression in a ref; an action's
code not read whole), 2 for a usage error: an action that was not checked is never cleared.

### Before you commit (`lazaret hook`)

`lazaret hook` checks the files being committed, as they are staged, and fails on `--ci`'s security and
supply-chain conditions: no BLOCKER finding (a credential, SQL built from strings), no CRITICAL
vulnerability, no supply-chain indicator (an install hook that downloads and runs code, a workflow that
sends out the repository's secrets, code that decodes and runs a payload) and no cross-file taint flow.
Duplication and maintainability, which `--ci` also gates, are not checked. Each file is scanned as a project
scan scans it, from git's index, so a partly staged file is checked as it will be committed. With no file
named it checks the files staged for commit; it prints what fails the gate, and the vulnerabilities of
MAJOR and above. Since 0.1.9.

With [pre-commit](https://pre-commit.com), the mirror repository installs Lazaret's wheel for your platform
by version:

```yaml
repos:
  - repo: https://github.com/lazaret-dev/lazaret-pre-commit
    rev: v0.1.9
    hooks:
      - id: lazaret
```

Without it, the git hook is an executable `.git/hooks/pre-commit` holding `#!/bin/sh` and `lazaret hook`. To accept a
finding, mark its line (Inline suppression, below); to leave files out with pre-commit, use its `exclude`.
Exit codes: 0 passed or nothing to check, 1 the gate failed, 2 usage error. The npm package has no `hook`
command yet.

## Detection capabilities

- **63 pattern rules** across Python, JavaScript, and SQL: injection (SQL/command/code), unsafe deserialization, SSTI, XXE, hardcoded secrets, weak crypto/ciphers, TLS/SSH verification, XSS sinks, prototype pollution, NoSQL injection, insecure config, Trojan Source bidi controls (S-BIDI), bugs, code smells, complexity, duplication.
- **SQL rules** (`.sql` scripts, stored procedures, migrations): `xp_cmdshell` OS execution, dynamic SQL built by concatenation, hardcoded credentials, `GRANT ALL`/`TO PUBLIC`, `OUTFILE`/`LOAD_FILE` filesystem access, `OPENROWSET`, disabled integrity checks, `TRUSTWORTHY ON`, `DELETE`/`UPDATE` without `WHERE`, `NOLOCK` dirty reads, and `SELECT *`. SQL is pattern-scanned (no taint/complexity metrics); comments are `--` and `/* … */`.
- **Comments are lexed, not guessed**: comment state (block comments, strings, JS template literals) is tracked across lines, and a line is skipped as a comment only if all of it is comment — `/**/eval(…)` or a minified file that opens with a `/*! license */` banner is scanned. JavaScript lines also end at U+2028/U+2029, as the runtime reads them. Where text reads two ways, it is a comment only if both readings agree: JSX element text, Python f-strings as 3.12+ reads them, MySQL strings with backslash escapes and MySQL's executed `/*! … */` are never taken for comments (nor for a place a suppression marker can hide).
- **Unicode tricks**: Python lines are matched in NFKC form (`ｅｘｅｃ(…)` is `exec(…)` to the interpreter); JavaScript identifier escapes (`\u0065val`) and U+FEFF-as-whitespace are normalized before matching; bidi control characters anywhere in a source line are S-BIDI (CRITICAL); and a name spelled with look-alike letters from another alphabet (a Cyrillic e in `\u0435val`), an invisible U+200C/U+200D, or in JavaScript a fullwidth letter, that reads as an ASCII name it is not, is SC-HOMOGLYPH — CRITICAL when it reads as eval, exec, require & co. or as another name in the file (`const \u0435val = eval` makes a second eval no rule or reviewer sees called), MAJOR when it only mixes alphabets; names are read in code only, not in comments, strings or regex literals (`/[a-z\u0430-\u044f]/` holds no name). Source text is read in Unicode 13.0 on every Python and Node version (a later code point is scanned and shown as U+FFFD), so results do not depend on the runtime's Unicode tables.
- **Taint tracking** (intra-file): follows user input (`request.*` in Flask and Django — `args`, `form`, `GET`, `POST`, `COOKIES`, `META`, `body`, … —, `req.*`, `argv`, decode functions) through variable assignments — including annotated and augmented assignments (`x: str = request.args[…]`, `html += …`) and JavaScript destructuring (`const { file } = req.query`) — and into Python f-strings and JavaScript template literals (`open(f"/srv/{name}")`, ``exec(`ls ${dir}`)``; a tagged template such as ``sql`…${id}` `` is parameterized and not read), over the lines of one statement, into sinks: SQL, command, code, path traversal (`open`, `codecs.open`, `send_file`, `shutil`, `os.remove`, …), SSRF, open redirect, XSS (Flask's `make_response` / `Response`, Django's `HttpResponse`, `Markup` / `mark_safe`, and what a Flask view returns), SSTI. Only the arguments that carry the injection are read: a query's bound parameters (`execute(sql, (x,))`), a response's headers, keyword arguments like `requests.post(url, data=…)`, a redirect to a path on the same site (`redirect("/user/" + id)`) and the code after the call are not. A path check that leaves the function (`if ".." in name: abort(400)`, `if not p.startswith(BASE): return`) clears path traversal. A taint lives in the function body it was made in; a reassignment in the same block replaces the value (`p = secure_filename(p)` is clean), one in a branch adds to it. A value written into a container taints it (`d["k"] = q`, `xs.append(q)`, `arr.push(q)`), followed by literal key (`d["other"]` stays clean); an element looked up by a request value (`users[req.params.id]`) or a `slice()` index is the container's, not the key's. An allowlist check (`if name in ALLOWED:`, `if (allowed.has(name))`, or one that leaves when it fails) clears the value where it passed. Findings name the tainted variable and where it originated.
- **Framework models: Flask, Django, FastAPI, Express** (both engines). Route handlers: the parameters a framework fills from the request are sources — a Flask view's URL variables (not `int`/`float`/`uuid`/`any` converters), a FastAPI path operation's parameters (not dependencies — `Depends(…)`, an `Annotated[…, Depends(…)]` alias, `…Dep` names —, `Response`, `BackgroundTasks`, nor a type that validates to no free text: `int`, `float`, `bool`, `UUID`, `Decimal`, dates, `Literal[…]`, constrained numbers, an Enum member), a Django view's URL parameters after `request` (not `pk`, `id`, `slug`, `…_id`, or typed ones); the interprocedural engine follows them into other functions' sinks too. Sources also include `request.query_params` / `path_params` (Starlette, FastAPI, Django REST framework), a websocket's messages, and Express's `req.url`, `req.originalUrl`, `req.path`, `req.hostname`, `req.get(…)` and a request named `request`. Sinks also include FastAPI's `HTMLResponse`, `RedirectResponse`, `FileResponse`; Django's `Manager.raw`, `RawSQL`, `QuerySet.extra`, `SafeString`; a jinja2, Mako or Django `Template` (in a file that imports one) and `Environment.from_string`; `httpx`; `asyncio.create_subprocess_shell`; Express's `res.send` / `write` / `end` (Express sends a string as HTML; a whole parsed object such as `res.send(req.query)` as JSON), `res.location`, `fs` writes and removals, EJS / Pug / Handlebars / Mustache / Nunjucks / lodash templates compiled from a value, `vm`, knex's and Sequelize's raw SQL, `got`, `needle`. Not sinks: a response with a non-HTML content type (`HttpResponse(body, content_type="text/plain")`, `res.type("text/plain").send(…)`), `send_from_directory`'s file name (Flask joins it safely) and Express's `sendFile` / `download` given a `root` (it refuses a path that climbs out), a redirect to a fixed host (`"https://github.com/…/%s" % rev`). What an ORM lookup returns (`get_object_or_404`, `Model.objects…`, `Model.query…`, `session.execute(…)`) and what a file read gives are not request data.
- **Interprocedural / cross-file taint** (`lazaret.scanner.flow`): whole-program analysis that follows untrusted data *through function calls and across files* — a source in one module reaching a sink in another is caught (`X-*` findings name both the source and sink locations), including a source returned by a helper and passed straight into a sink. Python is read into its syntax trees (Python 3.13's, by the native engine's parser, in both packages): calls resolve through imports (aliases, relative imports, re-exports), `self`/`cls`/`super`, constructors and typed locals; arguments bind like a real call (keywords by name, positional-only, `self` skipped); summaries are kept per sink category; module-level code and `if __name__ == "__main__":` blocks are analyzed; a worklist fixpoint composes `f → g → sink` chains. Taint flows through `await`, conditional expressions, containers and comprehensions, `for` targets, `match`, walrus and `self.attr`. JavaScript and TypeScript (0.1.7) are parsed too — the native engine's parser reads ES2025 with JSX, TypeScript and Flow annotations into ESTree trees (checked node for node against acorn on 21,295 real files, and against TypeScript's own parser for every call, function and JSX element of 9,416 TypeScript files), with no dependency — and followed the way Python is: each function gets a summary (which parameters reach which sinks, what it returns) computed to a fixpoint callees first, so `f → g → sink` chains of any length are found. Names resolve through scopes (hoisting, block scope, closures, catch clauses) and calls through relative `require()`/`import` (named, default and namespace imports, `require('./x').f()`, ESM and CommonJS exports, re-exports, `./x.js` naming `x.ts`, `import x = require()`, `export =`), object literals' methods, classes (`new C()`, `this`, `super`, static members, inheritance) and functions assigned to names. A call it can't resolve — through a package, a path alias or workspace package, or an object it can't identify — may reach any project function of that name (up to four); it binds nothing only on positive evidence: a Node built-in module, a member of a global like `JSON`, `Math`, jQuery's `$` or lodash's `_`, a built-in method name (`replace`, `map`, …) on an unknown receiver, a request's or a response's method, or a parameter or variable declared around the call. Values are followed through locals (per branch, merged; loops read again until they settle), destructuring, spreads, containers, template literals, closures, callbacks and a module's exported variables (`export const target = process.argv[2]` reaching `exec` in its importer); a sanitizer clears what it covers (a project function named like one, such as its own `escapeHtml`, is analyzed rather than trusted). For SQL a value must be joined into the query text, so a value bound as a parameter, a query passed through whole, or a tagged template (`` sql`…${id}` ``) is not a finding; a URL that starts with a fixed host or a path on this site (`'https://api.example.com/' + id`, `` `/profile/${u}` ``) is no SSRF or open redirect; a Server-Sent Events frame is no HTML. Express-style routes (`app.get('/p', fn)`, `router.route('/p').post(fn)`, `app.use(fn)`, a wrapped `asyncHandler(fn)`; Koa's `ctx`) give a handler the request and the response whatever their names; React's `dangerouslySetInnerHTML` is an XSS sink. A regular expression's `exec()` is not a command sink when the receiver is provably one — a `/…/` literal, `new RegExp(…)`, or a name declared once as one and used only as a regex; any other `.exec(` (child_process, shelljs, a receiver it can't identify) still is. Declaration files (`.d.ts`) are not read. The parser and the pass are the native engine's, so the npm package reports the same JavaScript flows. A file the engine can't parse is named in a Q-FLOW-SKIPPED note; the rest of the project is still analyzed. The JavaScript pass reads up to 8,000,000 characters of a project's code (a file over 2,000,000 is an X-FLOW-SKIPPED note) within a work budget proportional to its size, so a scan stays bounded; hitting a limit is a Q-FLOW-INCOMPLETE note.
- **Category-aware sanitizers** (SonarQube/Semgrep model): a value passed through a sanitizer stops being tainted for the categories that sanitizer covers, which is the main defense against false positives. `int()`/`Number()` (and Flask's typed `request.args.get(…, type=int)`) fully cleanse; `shlex.quote()` clears command injection only; `html.escape()`/`escape…()`/`DOMPurify.sanitize()`, an autoescaping `render_template()` and `jsonify()` clear XSS only; `url_for()` clears XSS and open redirect, Django's `reverse()` open redirect, and so does reading the Referer (a redirect "back"); `render_to_string()` and Starlette's `TemplateResponse` clear XSS; `os.path.basename()`/`secure_filename()`/`safe_join()` clear path traversal; DB-driver `.escape()` clears SQL, and in the interprocedural engine an ORM query builder (SQLAlchemy's `select(…).where(…)`, `filter_by`, `values`) binds its values. Using the *wrong* sanitizer for a sink (e.g. `html.escape` before a shell call) is still reported. Clearance propagates transitively through assignments and across function boundaries (a helper that wraps `shlex.quote` clears what `shlex.quote` clears).

- **CI files' hardening** (0.1.9, both engines): practices a pipeline should follow, checked in a project's GitHub Actions workflows and GitLab CI files (`.gitlab-ci.yml`, `*.gitlab-ci.yml`, a `.yml` under `.gitlab/`) and reported as security hotspots. Workflows: an action, a reusable workflow or an image not pinned to a full commit SHA or a digest (**SC-WORKFLOW-UNPINNED**, MAJOR; MINOR for GitHub's own actions at a version tag), a `pull_request_target` job that checks out the pull request's code (**SC-WORKFLOW-PR-CHECKOUT**, CRITICAL), a build cache restored in a release workflow (**SC-WORKFLOW-CACHE**), write permissions for every job or no `permissions:` at all (**SC-WORKFLOW-PERMISSIONS**), a job that can request an OIDC token and installs dependencies with their scripts (**SC-WORKFLOW-OIDC-INSTALL**), and a script fetched and run unread, `curl … | sh` (**SC-WORKFLOW-PIPE-SHELL**). GitLab: a file included from a URL (CRITICAL over plain http), a project's file or a component not pinned to a commit (**SC-GITLAB-INCLUDE**), an image without a digest (**SC-GITLAB-IMAGE**), `curl … | sh` (**SC-GITLAB-PIPE-SHELL**), a merge request's or a commit's text run as code (**SC-GITLAB-MR-TEXT**), and a job holding a publishing credential that installs dependencies with their scripts (**SC-GITLAB-TOKEN-INSTALL**). Only a CRITICAL one fails the gate's supply-chain condition: most repositories run an action at a version tag, and that condition is for indicators. A dependency tree's CI files are not read.
- **Self-publishing and hidden code (0.1.8)**: code that renames its package and publishes it — an assignment to an object's `name`, a write of that object to `package.json`, and `npm publish` (or pnpm, yarn, bun) run by an exec call: the registry floods' `auto.js` (SC-SELF-PUBLISH, CRITICAL; release tools publish but never rename); code after a run of 150 or more blanks on a line, standing in code rather than in a string or a comment, where editors and review don't show it (SC-OFFSCREEN-CODE: CRITICAL when it loads or runs more code, else MAJOR); and three more reasons an install script fails the install-script test: it runs `npm publish`, it collects npm access tokens (`.npmrc`'s `_authToken`, `npm config get …:_authToken`), or it runs a DLL of its own with `rundll32` or `regsvr32` (string pieces are joined first: `"rund"+"ll32"`).
- **Decoded payloads and staged downloads (0.1.8)**: the install-script and import-time tests read a file a second time with the strings it decodes as it runs decoded — `Buffer.from(…, 'hex' | 'base64').toString()`, `atob`, `bytes.fromhex` / `b64decode` / `unhexlify(…).decode()`, the file's own hex or base64 helpers, and its own XOR decoder (a function called five times or more with base64 or hex literals, whose calls turn into printable text with a short key among the file's strings: react-zutils kept the 83 strings of its browser stealer that way), with a constant array of strings read where it is indexed and `process["env"]` read as `process.env` — and a reason found only there says so (tailwind-book-icon kept every name hex-encoded: `require(g('6178696f73'))` is axios); (0.1.8) javascript-obfuscator's string arrays (the strings moved into one array read through an accessor: undecoded, base64 or RC4, rotated by its checksum loop, which is worked out as JavaScript does — nothing is run — and must hold), the proxy objects of its control-flow flattening (a short name reused in each function read as that function's object), string literals written wholly in `\x` / `\u` escapes, and a file's own character-code decoder whatever its arithmetic are read there too, so the tests see what such a file does — and install-time or import-time code built around such a string array is CRITICAL for that alone ("hides its code in a string array it decodes as it runs"); eval, `Function` or vm's `runIn…Context` given what any function computes from hundreds of character codes or a long literal is SC-EVAL-DECODER (CRITICAL); the received-code test also reads `Function.constructor`, a statement a formatter spread over several rows, a value carried by an environment variable, `getattr(m, 'x')` / `m['x']` (and a `getattr` name the file builds: `'pu' + 'll'`, a constant), a runner named through the builtins or the global object (`getattr(builtins, 'exec')`, `globalThis.eval`), TypeScript's `(0, ns.fn)(…)` and a runner handed to a call (`p.then(eval)`); a script downloaded or decoded, written to a file and run with a shell or an interpreter is CRITICAL ("downloads a script and runs it with bash"; litellm 1.82.7 wrote a base64 payload to `p.py` and ran it with `sys.executable`); and a script that an install hook, install script or import-time code starts with node or python (`spawn(process.execPath, [file], { detached: true })`, `fork(…)`, `subprocess.Popen([sys.executable, start])`), with bun or deno, or with any program a variable names given a file of code (a runtime it fetched: `execFileSync(bun, [path.join(dir, 'x.js')])`), is followed to the package file it runs, three starts deep, and tested like the one that started it. A program written in a string literal (for `node -e`) is read as its own code: the string is not a value the code around it receives.
- **Inline suppression**: `# nosec`, `// NOSONAR`, `-- nosec` (SQL), or `lazaret-ignore: RULE-ID[,RULE-ID]`, with an optional free-text reason after it (`# nosec - reviewed by bob`). The marker must be inside a real comment (not a string or an expression), on the flagged line or on a comment-only line directly above. SC-* (supply chain) and X-* (cross-file) findings are never suppressed, and nothing is suppressed in dependency files (`--deps`).
- **Report size stays bounded**: snippet lines are clipped to 240 characters (the flagged line is windowed around the match); findings identical on rule, file, line and message are reported once; and every non-security rule (anything but S-, T-, SC-, X- and SQL-) is capped at 200 per file and rule, with one Q-CAPPED note for the rest (it records how many it replaces, and the maintainability rating counts them, so a cap never changes the gate). Security findings are never capped. A 2 MB file of 130,000 repeated empty `catch` blocks on one line gives a 3 KB report (it used to be 88 MB).
- **Shell execution in JavaScript** (S-EXEC-JS): `exec`/`execSync` as a free call, destructured from `child_process`, or on any receiver (`cp.exec`, `child_process.exec`, `require('child_process').exec`) — but not on `this.`/`self.`/`super.`, not private `#exec` methods, and not method definitions (`async exec(…) {`, `exec(args) {`).

## Custom taint config

Pass `--taint-config path.json`. It extends the built-in model for both the intra-file and cross-file taint engines:

```json
{
  "python": {
    "sources":    ["mylib\\.read_untrusted", "flask\\.request\\.view_args"],
    "sinks":      [{"pattern": "mylib\\.run_shell", "category": "command injection"}],
    "sanitizers": {"full": ["mylib.validate_id"],
                   "partial": {"mylib.clean_cmd": ["command injection"]}}
  },
  "javascript": {
    "sources":    ["getUserInput"],
    "sinks":      [{"pattern": "runShell", "category": "command injection"}],
    "sanitizers": {"full": ["toSafeInt"], "partial": {"myEscape": ["cross-site scripting"]}}
  }
}
```

`sources` and `sink.pattern` are **regular expressions** matched against the call/attribute text; `sanitizer` names are **exact call names** (`module.func` or `func`). In the cross-file JavaScript pass the text is a member expression's (`ctx.request.rawBody`), a call's callee followed by `(` (`db.rawQuery(`, `getUserInput(`) or an assignment's target followed by ` =` (`el.innerText =`), so a pattern that names the call matches wherever it is written. `category` must be one of: `SQL injection`, `command injection`, `code injection`, `template injection`, `path traversal`, `server-side request forgery`, `open redirect`, `cross-site scripting`. A `full` sanitizer cleanses every category; a `partial` one cleanses only the listed categories. A ready-to-edit example ships as `examples/lazaret-taint.example.json`.

**A config inside the scanned repository is not trusted by default.** The repository controls that file, and sanitizers in it could silence real findings (declare `str` a sanitizer and a cross-file command injection disappears). So a `.lazaret-taint.json` in the scan root is loaded only with `--trust-repo-config` — otherwise the CLI prints a one-line note that it was found and not loaded — and even then only its `sources` and `sinks` are applied; its `sanitizers` are ignored with a warning. A used repository config is recorded in the report as a Q-TAINT-CONFIG note. A file you name with `--taint-config` is trusted fully.

Every field is type-checked (a string where a list is expected is an error, not a list of characters), and user regexes are guarded against catastrophic backtracking: at most 500 characters, no nested quantifiers, no repeated alternation, no backreferences, each match sees at most 2,000 characters of text, and the engine's linear-time regex engine must run them (the cross-file taint passes run them on it).

Rules that fail validation — unknown `category` (e.g. `"sql"` instead of `"SQL injection"`), missing/empty `pattern`, a wrong type, an unsafe regex — are **never silently dropped**: each prints a `warning:` naming the config file, the rule and the reason, plus the list of valid categories. When the config comes from an explicit `--taint-config`, or from the repository with `--trust-repo-config --strict-taint-config`, rejected rules additionally fail the run with exit code `4` — CI cannot silently lose coverage. An explicit `--taint-config` that can't be loaded at all (missing, unreadable, not a regular file, over 1 MB, bad UTF-8 or JSON, too deep, a huge integer) is also exit `4`, before scanning; a repository config that can't be loaded only warns, unless `--strict-taint-config` is set. (Quoting a category still needs the exact spelling; the warning lists all valid spellings.)

## Comparison vs. established scanners

Measured on one shared sample set in September 2026 and rerun for 0.1.7 and 0.1.8. Every tool read the same samples statically; nothing was installed or run. For 0.1.8 the PyPI samples were re-prepared from each release's own files (for 11 of them the first preparation read the upstream source tree the dataset ships beside some compromised releases, or an unrelated archive inside the package), and every tool was rerun on the ones that changed. **Lazaret's numbers on these samples are in-sample:** its 0.1.8 detectors were written while reading the benchmark's misses. A holdout of 745 other malicious releases of the same dataset (747, less two opened to diagnose a loss), which no detector was written from and which is looked at only in aggregate, measures what carries over (the second row).

| What was measured | Lazaret 0.1.8 | Lazaret 0.1.7 | Other tools on the same samples |
|---|---|---|---|
| Real malicious npm and PyPI releases caught at the strictest verdict (516 from a leading open dataset of malicious packages; in-sample for Lazaret) | **87%** SUSPICIOUS, 86% on what the code does; 90.3% with the registry's dependency history (live registry data) | 68% | GuardDog 71% high_risk |
| The same on a holdout: 745 other malicious releases of the dataset, none read while writing detectors | **85%** SUSPICIOUS, 98.6% of them on what the code does | 70% | not run |

| The same, counting the weaker verdict (Lazaret WARN, GuardDog suspicious) | 91% caught, 7.2% flagged | 77%, 7.5% | GuardDog 77%, 5.8% |

| Install-time blocking (`lazaret guard --plan npm install`, each npm sample served by a local registry) | 241 of 300 malicious npm releases blocked (80%: the guard blocks exactly those judged SUSPICIOUS; measured end to end at 242 before 0.1.8's behaviour pass); none of 219 popular npm packages | 165 of 300 (55%); 2 of 219 | Socket Firewall, Aikido Safe Chain and SafeDep pmg block at install too (not run here: each needs an account or a live service) |

On the holdout's 497 releases that share no code file with the benchmark's samples, 0.1.8 is SUSPICIOUS on 79.5% (0.1.7: 74%) and SUSPICIOUS or WARN on 86% (0.1.7: 82%), and its verdicts there rest on what the code does or a generic technique for 78% of those 497 (0.1.7: 55%, whose strict verdicts on new campaigns leaned on obfuscator names and a hook's tokens, which 0.1.8 no longer gives a verdict on alone); on the 248 campaign siblings of the benchmark's samples it is SUSPICIOUS on 97% (0.1.7: 63%). Read with care: the dataset's maintainers say most of it was found by GuardDog's own rules, which favors GuardDog, and part of the npm set is placeholders and proofs of concept with no payload at all, which no content scanner can catch. Of the 365 releases GuardDog calls high_risk, Lazaret calls 363 SUSPICIOUS; the other 2 are WARN, since 0.1.8 no longer gives a verdict on a list of services alone (javascript-obfuscator's names neither: it reads what the code builds instead, and code built around its string array) — and either tool's strict verdict covers 87.4% of the 516. The registry's dependency history needs the live registry (the benchmark's samples are files): it caught the 17 @mastra releases, which change no code, and none of the 429 popular packages. No popular package is SUSPICIOUS: the three that 0.1.8's detection rounds flagged are WARN or OK now that the engine reads code on its syntax trees (cypress's look-alike identifier is a keyword's look-alike, jiti's `eval` of transpiled code is a flow its tree doesn't confirm, and inspect-ai's encoded payload is held in a string). TruffleHog's strength, checking keys against their provider, can't apply to fake keys. Lazaret reads Python, JavaScript, TypeScript and SQL, plus config files for credentials (and since 0.1.9 a project's Go and Rust files for credentials, tokens and hidden characters); Semgrep, CodeQL and SonarQube cover 30+ languages and model many more frameworks, and CodeQL's whole-program analysis goes deeper than Lazaret's summaries.

Honest limits: the cross-file taint engine is summary-based and import-resolved — one summary per function, not per calling context — and it doesn't model every flow (in Python, constructor-argument → `self.attr` → method flows and dynamic dispatch; in JavaScript, a value stored in an object's field and read by another function (`this.cmd = c` in one method, `exec(this.cmd)` in another), a callback's parameters when an external function calls it (`promise.then(v => exec(v))`), a value set in one function and read in an unrelated one through a module variable, and JSX components' props, which are followed only when a component is called as a function); an object or array holds everything written into it rather than per key, which can over-report; a call on an unknown receiver only matches rare method names, and one it can't resolve matches up to four project functions of that name, which can over-report in bundled or minified code; it is built to catch accidental flows in ordinary code, not code written to evade it (a value routed through dynamically built calls or `eval`); framework modeling covers Flask, Django, FastAPI and Express-style routes; and SCA matches against a CVE bundle you build from public feeds with `lazaret-sca --update-bundle` (Lazaret ships no vulnerability database of its own). For deep dataflow on large or polyglot codebases, consider Semgrep/SonarQube alongside Lazaret.

## Dependency CVE scanning (SCA)

`lazaret-sca` inventories the npm, PyPI, Go and Rust packages actually installed or pinned in a project — `node_modules` (nested copies included), `package-lock.json` v1–v3 (nested entries, `npm:` aliases, workspaces), `yarn.lock` (v1 and berry), `pnpm-lock.yaml` (v5/v6/v9), `bun.lock`, virtualenv `site-packages`, `requirements*.txt` and `requirements/*.txt` (following `-r`/`-c`), `pyproject.toml` (PEP 621 dependencies, dependency groups, `tool.poetry`), `Pipfile.lock`, `poetry.lock`, `uv.lock`, `pylock.toml` (PEP 751), `setup.py`, Go's `go.mod` (every `require`, with its `replace` lines applied), `go.sum` (every version with a zip hash, for a module whose `go` directive is before 1.17, when `go.mod` does not list everything the build needs) and `vendor/modules.txt` (the modules it vendors, not the replacements it only records), the modules a `go.work` uses, Rust's `Cargo.lock` (a registry crate at its locked version) and the root `Cargo.toml` with its workspace members' — and a `go.mod` or a `Cargo.lock` below the root that none of these names is counted in a warning, not read — and matches each `name@version` against a CVE bundle built from public data: OSV advisories (GitHub Security Advisories, the PyPA advisory database and OpenSSF malicious-package reports, with their affected-version ranges), CISA's Known Exploited Vulnerabilities catalog, and EPSS scores. Manifests are decoded like source files (a UTF-8 BOM is dropped, UTF-16 is read as such), and one that is there but can't be read or parsed is named in a warning.

```bash
lazaret-sca --update-bundle                       # download the feeds into ./cve-bundle.json
lazaret-sca . --bundle cve-bundle.json            # scan and report
lazaret-sca . --bundle cve-bundle.json --ci       # exit 1 if the gate fails
lazaret-sca . --bundle cve-bundle.json --update-bundle --ci   # refresh the bundle, then scan
lazaret-sca . --inventory-only                    # what is installed or pinned (no bundle needed)
lazaret-sca . --bundle cve-bundle.json --sarif sca.sarif --baseline prev.json
lazaret-sca --update-bundle --bundle-format index --bundle cve-bundle.lzx   # the indexed form (below)
```

`--update-bundle` downloads three public feeds (no account or API key) and writes the bundle to `--bundle` (default `cve-bundle.json`): OSV's npm, PyPI, Go and crates.io exports (`storage.googleapis.com/osv-vulnerabilities/{npm,PyPI,Go,crates.io}/all.zip`), CISA's KEV catalog (its JSON feed, or CISA's GitHub mirror when the feed can't be reached), and the day's EPSS scores. OSV records that alias one another (a GHSA advisory and the PYSEC record for the same CVE) become one advisory, named by its CVE. OSV names are package-manager names, so each of these entries matches only its own ecosystem and its own name: an npm package called `requests` never matches PyPI's `requests`, and `babel-core` never matches `@babel/core`. The update is all or nothing: a feed that fails its checks (an empty KEV catalog, an export with no advisories for its ecosystem, a damaged archive) stops it, and the new bundle replaces the old one atomically, so a failed update leaves the old bundle in place for the freshness condition to age. Downloads are https only, with a byte budget each, and what a feed decompresses to is budgeted too: the EPSS reader charges every decompressed byte and caps the length of a line, and an OSV export's zip directory is checked against the record budget before it is parsed. A `file:` URL or a local path reads a mirror instead (`--osv-url /mirror/{ecosystem}/all.zip`, `--kev-url`, `--epss-url`); `--no-epss` skips EPSS. The OSV npm export is large (it holds every malicious-package report), so in CI refresh the bundle once a day and cache it rather than downloading it for every scan. Each bundle records where its data came from and the attribution its sources ask for.

A known-exploited (KEV) CVE on an installed version is a **BLOCKER**, and so is a version named in a malicious-package report (SCA-MALICIOUS: the release is malware, so remove it and rotate the credentials the machine could reach); otherwise severity follows the CVSS 3.x base score or the advisory's severity label. Nothing is ever cleared by default: a package with no range data, and an installed version or range bound that can't be compared (`*`, `2.*`, a git or URL dependency, an unpinned name), is reported as SCA-CVE-UNKNOWN. An advisory covering every version (a malicious package, a flaw with no fix) matches whatever is installed or pinned, unpinned names included. Versions compare the way each ecosystem does: PEP 440 for PyPI (epochs, pre/post/dev releases, `1.0 == 1.0.0`; a public bound ignores a `+local` label, as pip does) and semver 2.0 for npm (prerelease identifiers compared field by field, build metadata ignored). Package names are normalized per ecosystem (PEP 503 for PyPI); a scoped npm package never matches its unscoped namesake (`@types/lodash` is not `lodash`).

Go and Rust (0.1.9): Go module paths are kept as written (they are case-sensitive) and crate names fold case and `_` to `-`, as crates.io does; versions compare as SemVer (Go's `v` prefix and pseudo-versions included). A module replaced by a version of itself is that version; replaced by another module, it is that module, and the one it replaces stays in with no version, so its advisories report as SCA-CVE-UNKNOWN. A module replaced by a directory, a path dependency and a workspace member are the project's own code. A crate from git or another source has no version. The standard library and the toolchain are not matched (`go.mod` names a minimum Go version, not the toolchain that builds), nor are RustSec's `unmaintained` and `notice` advisories. A bundle made before 0.1.9 has no Go or crates.io advisories (its `sources` lack `osv:go`, `osv:crates`): for a project with Go or Rust dependencies it fails the gate rather than report none.

**An indexed bundle.** `lazaret-sca --update-bundle --bundle-format index --bundle cve-bundle.lzx` writes the same advisories as a file a scan reads only the parts of it needs, instead of parsing a 90 MB JSON document: on a synthetic bundle the size of OSV's, opening it and matching 2,000 dependencies takes 0.2 s and 42 MB instead of 6.9 s and 640 MB, with the same matches in the same order. `--bundle` reads either kind (told apart by their first bytes). The file is checked whole when it is opened (its length, the checksums of its header and tables, their layout and order) and each record when it is read; a damaged file exits 4, also when a record is found damaged in the middle of matching, and no report is written. Checksums find damage, not tampering: like the JSON one, a bundle you don't trust can say nothing is vulnerable. `python -m lazaret.scanner.sca_index build IN.json OUT`, `check FILE` and `info FILE` convert and check one. The JSON bundle stays the default.

The bundle is validated entry by entry: malformed entries are skipped and counted in a warning, and a bundle that can't be used exits 4, as does an update whose feeds can't be read (one whose bundle can't be written exits 3). A missing, unparseable or future `generatedAt` fails the freshness condition (naive timestamps are read as UTC). Output uses the same report format (JSON, HTML, SARIF), safe report paths (`--out-dir`, `--force-overwrite`), baselines and exit codes as `lazaret`.

## Registry scanning (npm, PyPI, Go, crates.io, VS Code extensions)

Audit published packages for supply-chain compromise before you depend on them. Archives are downloaded from `registry.npmjs.org` / `pypi.org` (Go modules from `proxy.golang.org`, crates from `static.crates.io`, VS Code extensions from `open-vsx.org` and the Visual Studio Marketplace) and scanned **in memory** (never extracted — immune to tar-slip). Scan state is tracked in a database so you can do full or incremental sweeps.

```bash
lazaret-registry add npm:express pypi:requests   # track packages
lazaret-registry scan npm:left-pad@1.3.0         # scan a specific version
lazaret-registry scan pypi:six --full            # full ruleset, not just supply-chain
lazaret-registry scan go:github.com/pkg/errors   # a Go module's latest version (since 0.1.9)
lazaret-registry scan crates:fnv@1.0.7           # a crate version (since 0.1.9)
lazaret-registry scan openvsx:redhat.vscode-yaml  # a VS Code extension on Open VSX (since 0.1.9)
lazaret-registry scan vscode:redhat.vscode-yaml   # one on the Visual Studio Marketplace (since 0.1.9)
lazaret-registry scan-all                        # scan latest of every tracked package
lazaret-registry scan-all --rescan --ci          # re-scan all; exit 1 on SUSPICIOUS or INCOMPLETE
lazaret-registry list                            # tracked packages + last verdict
lazaret-registry report npm:left-pad@1.3.0       # stored findings for one scan
lazaret-registry scan pypi:litellm --timings     # and where the time went, on stderr
```

**The network (since 0.1.9).** The registry's requests go through Lazaret's own HTTPS client, in the native library (`rust/crates/lazaret-net`, on tiny_https, which is in this repository: TLS 1.3, and TLS 1.2 with a server that speaks nothing newer, no dependencies). Each caller's rule is checked on the first URL and on every redirect before anything connects: https only, the registry's own hosts (a `*.` host is one DNS label, on the default port), no credentials in a URL, with a byte budget, timeouts and a redirect limit. Connections are kept and shared: documents (metadata, API answers) go over HTTP/2 where the server offers it and downloads over HTTP/1.1, which measured faster for each (`LAZARET_HTTP=2` or `LAZARET_HTTP=1.1` uses one for everything); documents come compressed (gzip, decoded within the request's budget: npm's packuments are 5 to 13 times smaller), downloads byte for byte as published (`LAZARET_GZIP=0` asks for nothing compressed, for a fast link to npm, whose CDN compresses a large document as it sends it). From a cloud machine against the real registries, 200 npm documents fetched by 16 threads took 0.6 s instead of 8.3 s, and 100 npm tarballs by 8 threads 0.4 s instead of 2.9 s. Trust anchors come from `SSL_CERT_FILE`, else the system's CA bundle, else what Python's `ssl` loads (the system's store on Windows); the proxy is the one urllib would use (`HTTPS_PROXY` and `NO_PROXY`, or the system's settings). Python's urllib (OpenSSL) sends a request instead where the native library is missing, through a proxy reached over TLS, and when `LAZARET_NETWORK=python` asks for it. Neither goes below TLS 1.2: a server that speaks nothing newer than TLS 1.1 is refused. tiny_https has not had an independent review (its own README says so); `LAZARET_NETWORK=python` keeps OpenSSL. The guard's downloads, the `github:` and `gitlab:` sources and the SCA feeds go the same way, credentials included (a private registry's token or login, `GITHUB_TOKEN`, `GITLAB_TOKEN`): the client gives each hop, the request and every redirect, the credentials of its own host and no other's, before anything is sent there, so a redirect to another host never carries a token on. A secret being verified goes over it too, to its provider's host alone; plain http to a registry on this machine stays on urllib. The same library checks the Go checksum database's answers (the signed tree head and the tiles that prove a record is in it, as the go command does), so a `go:` module's hash is the one the database has signed, not only the one a TLS connection brought.

Registry results are always redacted, on screen and in the state DB: a secret finding's line is stored as a placeholder naming the rule and the line's length, and credentials on the lines around any finding are masked, because the DB is read back by `report`, the MCP tools and anyone sharing a Postgres database. `--no-redact-secrets` has no effect here (the original lines are in the package's archive); it applies to project scans.

Each scan answers one question, "does this package look malicious?", with a verdict and a one-line reason:

| Verdict | Meaning |
|---|---|
| **SUSPICIOUS** | A strong supply-chain indicator: code that runs what it decodes or receives over the network, code hidden in hex escapes, or an install hook, a script it runs or import-time code that sends data read from the machine over the network (the environment, credentials, files, what local commands report; a known exfiltration endpoint names where it goes), plants persistence, or runs a download through a shell. Obfuscation alone (`_0x` names, a packer) is a weaker indicator since 0.1.8: what the obfuscated code does is read instead. |
| **INCOMPLETE** | Part of the package couldn't be scanned, so it can't be cleared. Nothing strong was found in the part that was scanned. Causes: a source file over the size limit (`--max-source-bytes`, default 16,000,000 bytes); too many files or artifacts; the download budget (`--max-download-bytes`) or the 200 MiB per-file download limit; the decompression budget (every decompressed byte counts) or the per-archive time limit (`--scan-timeout`, default 120 s); an archive in the wrong codec (bz2/xz served as `.tgz`), a truncated stream, trailing data, an invalid tar header or entries after an end-of-archive block (npm's extractor would still read them); a source file that isn't text; an unparseable root `package.json` or `binding.gyp`; an entry point or hook target that can't be read; a Go module's or a crate's code over 300 million characters, more than its reader holds at once (since 0.1.9). |
| **WARN** | Weaker indicators or capabilities worth a look: an install script, shipped binaries, nested archives, opaque blobs. Plenty of legitimate packages do these things (esbuild and puppeteer download a platform binary at install; setuptools and pip ship Windows launchers). |
| **OK** | None of the above. |

Weaker indicators inside test code are listed as inventory and don't count, since tests aren't imported or run when a package is installed; strong indicators count wherever they are. Test code means exact directory names (`test`, `tests`, `testing`, `__tests__`, `spec`, `specs`, `fixtures`, `__fixtures__`, `testdata`, `test_data`, `test-data`, `test-fixtures`, `unittests`, `test cases`) or test file names (`*.test.js`, `*.spec.js`, `test_*.py`, `*_test.py`) — never a file reachable from `main`/`bin`/`exports` (`index.js` by default), an install hook, or `setup.py` and its local imports. **Secrets and code-quality findings are reported but never decide the verdict**: a test key inside someone else's package isn't a threat to you. With `--ci`, SUSPICIOUS and INCOMPLETE fail the run; a partial scan never passes.

Only the scripts npm runs on install count as install hooks (`preinstall`, `install`, `postinstall`, and a root `binding.gyp`, which is npm's implicit `node-gyp rebuild`, with its actions and the command expansions that run a file of the package); publisher-side scripts like `prepack` run only on the maintainer's machine. Lazaret reads each hook's command as a program (what its network commands send, the code it hands an interpreter inline) and follows it to what it runs — commands are tokenized like a shell (`cd dir && node x`, `bun run x.js`, flags, `sh ./install.sh`), targets resolved the way Node resolves them (`x`, `x.js`, `x/index.js`) — and judges it by what that script does. For PyPI, an sdist's `setup.py` and any in-tree PEP 517 build backend are install scripts too, with the modules they import from the sdist (at its root, in `src/` or in a `backend-path` directory, and through relative imports; every import is followed to the end, a module named by a literal to `importlib.import_module()`, `__import__()` or `runpy.run_module()` too), checked for Python network calls and environment/credential reads, and for the shapes listed under Supply-chain indicators above (encoded PowerShell, stager strings, reverse shells, host information sent out, and a download that is run). Code that runs when the package is loaded — what `main`/`bin`/`exports` reach; a wheel's or an sdist's top-level packages and modules and the modules they import, followed the same way — gets a narrower version of the test, SC-IMPORT-RISK (MAJOR, so WARN, unless it is one of the CRITICAL shapes no library needs): the whole environment serialized or a credential store read and sent over the network (CRITICAL wherever it goes since rule set 2.17; a store is an SSH key, git credentials or browser storage, and since 0.1.9 the cloud's and the registries' credential files too: `~/.aws/credentials`, `~/.kube/config`, `~/.docker/config.json`, gcloud's and Azure's, `.npmrc`, `.pypirc`, `.netrc` …), what local commands print about the machine sent (CRITICAL too), a download piped into a shell by an exec call, or code it receives over the network run as code or as a command (`exec(requests.get(u).text)`, an https.get body handed to eval), deserialized (`pickle.loads`, unsafe `yaml.load`, `unserialize`), used as a dynamically imported module name, or written to a file that the same code then runs; and since 0.1.9 a package manager's install of a package the release's manifest does not name (`npm install x`, `pip install x`, as a command line or a program's argument list: CRITICAL, in registry and guard scans, where the manifest is known; in Python, in a function's body only when the module runs the function as it is loaded). Reading or listing environment variables, a tool reading its own config (`.npmrc`, `.pypirc`), or a cloud metadata address doesn't count, and neither do comments and docstrings: a file is read without them, so a docstring naming ``id_rsa`` or showing an installer's `irm … | iex` is documentation, not code — unless the file reads its own source (`open(__file__)`, `__doc__`, `readFileSync(__filename)`, a function's `.toString()`), where a comment may hold what it runs or the address it sends to. Code run from what a file reads back from itself, or from a data file shipped next to it (`exec(open(join(dirname(__file__), 'logo.png')).read())`), is CRITICAL in install scripts and at import time, whether it is read at once or asynchronously (a `readFile` callback's data, a `.then()` parameter, `with open(…) as f`: react-thunk-log decrypted and ran its own LICENSE).

Since 0.1.8 the registry also reads the rest of a package's JavaScript and Python — what it runs only when it is used, not at install or import: a logger's constructor, a middleware, a script a CLI spawns — for those CRITICAL shapes (SC-USE-RISK), leaving out tests, examples, docs, demos, benchmarks and a web app's static assets, and not reading on once the package is SUSPICIOUS. It reads the smallest files first, up to 24,000,000 characters per release file, so every machine reads the same ones, and when that leaves code unread the result says how much (`useTime` in the JSON, a line in the summary): next's 74 million characters of such code are read in part. The same files are read as one package by the cross-file follower (a file that runs what another file of the release received over the network is SC-IMPORT-RISK, CRITICAL, naming both; since 0.1.8 also when the value is handed over through an event emitter, `bus.emit('code', data)` in one file and `bus.on('code', eval)` in another, or to a function that hands it on to another file's runner, up to 16 hops; with `--deps` the top-level modules a distribution's RECORD lists are one package too), and a script an install script or import-time code starts with node or python is followed to the file it runs. And it compares a release's dependencies with those of the release published before it: a dependency first published less than 7 days before the release, outside the package's npm scope and from an account that doesn't maintain the package (npm's maintainers; PyPI's owners, maintainers and organization), is SC-NEW-DEPENDENCY (CRITICAL; MAJOR under 30 days). The @mastra compromise changed no code: each release only gained `easy-day-js`, created 19 hours before. That costs one registry document for the package and one per added dependency (at most five), none for a release without dependencies; a document over the metadata budget or a registry that doesn't answer is no finding, and `LAZARET_NO_DEPENDENCY_HISTORY=1` turns the comparison off. Since 0.1.9 an npm or PyPI release's provenance is checked too: the attestations npm lists in a version's `dist.attestations` and PyPI's PEP 740 provenance of each file are verified by the native library (the signature, Sigstore's certificate chain at a time its transparency log vouches for, and a subject with the file's digest), and the release is compared with the one before it. An attestation that is not about the file, or not signed by its signer's key, is SC-PROVENANCE-INVALID (CRITICAL); a release without the provenance the one before had is SC-PROVENANCE-DROPPED, and one built from another owner's repository than the one before (by the repository's and owner's IDs, which a rename keeps) SC-PROVENANCE-REPO-CHANGED (both MAJOR; a repository of the same owner is INFO); an attestation that could not be checked for a reason that is not the file's (a log or authority the shipped trust does not know) is SC-PROVENANCE-UNCHECKED, INFO. On the popular set's 1,205 releases (259 npm and 171 PyPI releases with verified provenance, none invalid or unchecked), one is WARN for it: why-is-node-running 3.2.2, published without the provenance 3.2.0 and 3.2.1 had. ultralytics 8.3.45 and 8.3.46 (December 2024) were uploaded with a stolen token and had none of the attestations the releases before had. The result's `provenance` says who built the release (repository, workflow, ref). It costs npm's abbreviated document for the package and the attestations of this release and the one before, or PyPI's Simple API document and one provenance document per file; the trust is Sigstore's trusted root and npm's keys as shipped (`LAZARET_SIGSTORE_ROOT` and `LAZARET_NPM_KEYS` name newer copies), and `LAZARET_NO_PROVENANCE=1` turns the check off. The guard does not check provenance yet. A release whose name, or a dependency it declares, is one change from one of the 5,000 most-downloaded packages of its registry — a character added, dropped or changed, two swapped, the separators changed — is SC-TYPOSQUAT (MAJOR): `requesxs` and `python-dateuti` among the benchmark's malicious releases, `@hestjs/core` for `@nestjs/core` as a dependency. A name the popular lists know is never one (`mysql2`, `delegates`, `fastai`), and neither is a name near a popular one under 5 characters or near one in its own npm scope (one owner names both). npm names are also compared with Node's built-in modules named with a separator: a dependency on `child-process` installs a stranger's package, since `require('child_process')` loads the built-in. An npm release's runtime dependency that no file of it names — no text quotes it as a module or package name, no other field of `package.json` names it — and that is neither one of npm's 5,000 most-downloaded packages nor in its own scope is SC-UNUSED-DEPENDENCY (INFO): it is installed, and its install scripts run, for nothing the package does. On its own that is context (builds inline dependencies and keep them listed); a brand-new one is SC-NEW-DEPENDENCY, CRITICAL, whatever its age under 30 days. Since 0.1.9 a Go module's path, or one its `go.mod` requires, is compared part by part with the 4,893 modules awesome-go lists or Debian packages (no Go registry publishes downloads): its owner one change from a well-known module's, its separators changed or a word like `-go` added, with the repository the same (`github.com/shopsprint/decimal`, `github.com/boltdb-go/bolt`); its host one change, the rest the same; a gopkg.in name one change. Anyone can create an owner on GitHub, and only its owner can add a repository to it, so an owner or host of a well-known module is never a look-alike, nor is a module of the module's own owner; another owner's module of the same name is a fork, not flagged. A crate's name, or a crate its `Cargo.toml` depends on to build (not a `[dev-dependencies]` one, which is never built for a user), is compared as npm's and PyPI's names are, with the 5,000 crates crates.io counts the most downloads of in 90 days: `proc-macro1` for `proc-macro2`, `rustdecimal` for `rust_decimal` (2022's CrateDepression squat). Names are folded as crates.io folds them (case, and `_` as `-`: `rust_decimal` and `rust-decimal` are one crate there). A crate release is compared with the one published before it as npm's and PyPI's are, from the sparse index alone (its lines are in publishing order, each with its `pubtime`): a crate it adds as a normal or build dependency, first published less than 7 days before, is SC-NEW-DEPENDENCY (CRITICAL; MAJOR under 30 days), unless an owner of the release's crate owns it too (crates.io's API, asked one request a second, as its crawler policy asks). A VS Code extension (since 0.1.9: `lazaret FILE.vsix`, `--extensions`, and the registry's `openvsx:` and `vscode:` scans) is named `publisher.name`, and anyone can create a publisher: its identifier, or one it brings (`extensionDependencies`, `extensionPack`), one change from a most-installed extension's of another publisher, or its publisher one change from such an extension's publisher, its separators aside, is SC-TYPOSQUAT (MAJOR): `juanbIanco.solidity` (a capital I for the l) cloned `juanblanco.solidity` on Open VSX in 2025, and `juan-bianco.solidity-vlang` came next. Another publisher's extension of the same name is a fork or a build, not flagged, nor is one of the extension's own publisher or of a publisher of fewer than six letters and digits; the targets are the 1,000 most-installed extensions of the Visual Studio Marketplace and the 1,000 most-downloaded of Open VSX (1,568 extensions; `scripts/fetch-top-extensions.py` saves both registries' rankings for a refresh). A release on Open VSX or the Marketplace is compared with the version its registry published before it on the extensions it brings: one first published less than 7 days before, of another publisher (on Open VSX, not published by the account that published the release), is SC-NEW-DEPENDENCY (CRITICAL; MAJOR under 30 days), the way GlassWorm's operators brought a malicious extension in through benign ones' `extensionPack` in 2026. The lists (`lazaret/registry/popular_names.json`) come from npm-high-impact (MIT), Top PyPI Packages (CC BY 4.0), crates.io's API (crate names only), awesome-go (MIT), Ubuntu's indices of Debian's Go packages (module paths only) and Open VSX's API (extension identifiers only), with their sources and licences in the file; `scripts/update-popular-names.py` rebuilds them.

Since 0.1.9 a Go module's code and a crate's code are read the same way (`lazaret guard go`, `lazaret guard cargo`, `lazaret-registry scan go:…` and `crates:…`): the engine's Go and Rust readers evaluate the code rather than match patterns over it, following the package's own functions across its files and the strings they build, and record the processes started, the data sent, the names looked up (DNS TXT records too), the files written and run and the libraries loaded. A Go package's `init` functions, the initializers of its package-level variables and a cgo constructor run when any program that imports the package starts, so what they reach gets the import-time test (SC-IMPORT-RISK); a crate's build script and a procedural macro run on the machine that builds a dependent, so they get the install-script test (SC-INSTALL-HOOK, CRITICAL), and a `#[ctor]` the import-time test; the rest gets the use-time test (SC-USE-RISK), within the same 24,000,000 characters. Test code no build of a dependent compiles (`*_test.go`, `testdata/`; `tests/`, `benches/`, `examples/`, and what `#[cfg(test)]`, `#[test]` or `#[bench]` marks in `src/`) is not read, `//go:generate` commands are listed (SC-GO-GENERATE, INFO), and every `.go` and `.rs` file gets the file rules, as a package's JavaScript and Python do; one over the size limit makes the scan INCOMPLETE. The Rust crate inside a PyPI sdist (maturin, setuptools-rust: pip has cargo build it when it installs the sdist) is read the same way: each directory of the sdist with a `Cargo.toml` is a crate, and a `.rs` file belongs to the nearest one above it (none: cargo never builds it); its build script and procedural macros are install scripts (SC-INSTALL-HOOK, CRITICAL), a `#[ctor]` runs when the extension module is loaded (SC-IMPORT-RISK), and the rest gets SC-USE-RISK, the sdist's crates sharing one 24,000,000-character share. Of 72 popular PyPI sdists with a crate (permissive licences only), reading their Rust makes two more WARN, for a 200-digit table and hex test vectors in `#[test]` functions, and none SUSPICIOUS: 65 are OK, 6 WARN, and 1 SUSPICIOUS for its Python, not its Rust (rumdl: a false positive of the use-time test on two maintainer scripts). A module or a crate used to be INCOMPLETE whatever it held; of Ubuntu 24.04's packaged Go modules and crates (1,953 and 2,120, those whose licences allow it) none is SUSPICIOUS, 2.0% and 1.4% are WARN, for base64 and hex constants, archives and binaries, and 2 are INCOMPLETE (Debian packs aws-sdk-go-v2's and azure-sdk-for-go's modules as one tree of 344 and 513 million characters, more than a reader takes at once).

What actually runs is what gets scanned: `main`/`bin`/`exports` targets (subpath patterns like `"./*": "./lib/*.js"` are expanded against the archive) and the local files they `require`/`import` are scanned as JavaScript whatever their extension, extensionless files with a `#!` line by their interpreter, and `.pth` files in wheels (Python executes their `import` lines at every interpreter start) as SC-PTH-EXEC. A wheel's top-level `sitecustomize` / `usercustomize` module (also in `.data/purelib` or `platlib`) is imported at every start too: SC-SITECUSTOMIZE, MAJOR, or CRITICAL when it fails the install-script test. Archive members are read the way installers extract them: in-archive hardlinks and symlinks in sdists and wheels are resolved and scanned under the link's name (npm drops links, as its extractor does); links that escape the archive, duplicate paths after normalization and unsafe paths are SC-ARCHIVE-LINK / SC-ARCHIVE-DUP / SC-ARCHIVE-PATH (MAJOR), and so is an entry with no name (SC-ARCHIVE-PATH); two paths that differ only by case or Unicode normalization, one file on macOS and Windows (the later entry's bytes under the earlier's name), are SC-ARCHIVE-DUP (MAJOR), and a twin of a file that runs is read as one that runs; a zip entry whose Info-ZIP Unicode Path field names it otherwise than its header is read under each name an installer uses (pip from Python 3.12 and VS Code take the field's, older pips the header's) and is SC-ARCHIVE-PATH (MAJOR), and one that zipfile from Python 3.12 refuses makes the release INCOMPLETE; a tar entry of a type tar has no file meaning for (a device, a FIFO, a type letter it doesn't know), which cargo and pip unpack as a regular file, is read as one and is SC-ARCHIVE-TYPE (MAJOR; npm's extractor skips them, and so does the scan of an npm tarball); zip entries whose bytes overlap, the shape of a zip bomb, are SC-ARCHIVE-OVERLAP (MAJOR), and an LZMA entry declaring a dictionary over 64 MiB is not decompressed (the member is unread, so the release is INCOMPLETE). Members are decoded as their runtime reads them (BOM, UTF-16, PEP 263 cookies incl. UTF-7 and unicode_escape), and a file isn't skipped as "binary" just because it contains accented text or a NUL.

Package specs: `npm:name`, `npm:@scope/name`, `pypi:name`, `go:module/path` and `crates:name`, each with an optional `@version` (a Go version is `v1.2.3`; a crate's is SemVer without the `v`). A Go module is the zip `proxy.golang.org` serves for it, checked against the `h1:` hash `sum.golang.org` publishes (a host other than the one that served it), and that answer is checked as the go command checks it (since 0.1.9): the database's signature on its tree head, with the key Go pins, and the record's place in that tree, proved from the database's tiles, and a crate is the `.crate` file `static.crates.io` serves, checked against the SHA-256 its sparse index (`index.crates.io`) lists; latest means the proxy's `@latest` and the highest crate version that is not yanked. An Open VSX extension (`openvsx:namespace.name`, since 0.1.9) is every `.vsix` its version is published for, one per target platform the editor installs (each is scanned and the worst decides, as a PyPI release's wheels do), each checked against the SHA-256 Open VSX publishes beside it, and read as `lazaret FILE.vsix` reads one (see *VS Code extensions* above); latest is what Open VSX calls latest, which can be a pre-release. The result says whether the namespace is verified (its owners are known and the publisher is one of them) and who published the version. A Visual Studio Marketplace extension (`vscode:publisher.name`, since 0.1.9) is resolved through the gallery query VS Code sends, latest being the newest release (VS Code's choice; a pre-release only when there is no release), and its files are read the same way; the Marketplace publishes no digest, so they are scanned unverified, and the result says so, with whether the publisher's domain is verified and its install count. (The Marketplace's terms of use say its extensions are for Microsoft's products; an extension VS Code installed is also scanned where it is installed, `lazaret --extensions`.) A download that does not match is never scanned (SC-DIGEST-MISMATCH, the error npm's and PyPI's get). Go modules and crates have no `discover` yet, and Go modules no SC-NEW-DEPENDENCY. VS Code extensions have neither yet. For PyPI, every artifact of the release is scanned — the sdist and each distinct wheel, each checked against its own digest — and the verdict is the worst one, with per-artifact detail in the result and the state DB (`--max-artifacts`, default 200). The release's files share the engine's answers: content that several of them hold (the same modules in each wheel and the sdist) is read once, and an answer the engine could not finish is never reused (since 0.1.9; `LAZARET_NO_CACHE=1` turns it off). Sizes declared in PyPI's metadata are checked before anything is downloaded: a file over the 200 MiB per-file limit is not fetched, and the whole release must fit in `--max-download-bytes` / `LAZARET_MAX_DOWNLOAD_BYTES` (default 2 GiB). Artifacts skipped for any of these limits are listed in `skippedArtifacts` and make the verdict INCOMPLETE — numpy (66 files, 0.8 GiB), pillow and grpcio fit; a release like torch (24 wheels of up to several GiB, 7 GiB in all) stays honestly INCOMPLETE. Archives are recognized by name as pip does (`.tar.gz`, `.zip`, `.tar.bz2`, `.tar.xz`, `.tlz`/`.tar.lz`/`.tar.lzma`, ...). Files PyPI lists as neither sdist nor wheel are listed in `skippedArtifacts` too: eggs and installers pip never installs don't count, but an archive pip could still pick by its name (a `bdist_dumb` `.tar.gz`) makes the verdict INCOMPLETE. pip installs a wheel when one matches, so scanning only the sdist would miss the code you actually get.

Already-scanned versions are skipped unless `--rescan` is passed: `scan-all` resolves each package's latest version first and doesn't download what it has already scanned, so incremental sweeps are cheap. A skipped version's stored verdict still counts: with `--ci`, a version already recorded as SUSPICIOUS or INCOMPLETE fails the run without `--rescan`. In `scan`, `scan-all` and `discover --scan`, a package that fails to scan or store is reported, the sweep continues, and the command exits 1 at the end with a one-line summary of the failed packages on stderr.

### Discovering new packages

Instead of a fixed watchlist, you can pull packages **newly published or updated** and scan them — useful for supply-chain threat hunting across the ecosystem:

```bash
lazaret-registry discover --since 1h                       # newest 50 new/updated PyPI+npm packages
lazaret-registry discover --since 1h --ecosystem npm --limit 0   # every npm package the walk reaches
lazaret-registry discover --resume --scan --ci             # everything since the last --resume run; exit 1
                                                           # on SUSPICIOUS, INCOMPLETE or a coverage gap
lazaret-registry discover --resume --ecosystem pypi --add  # just add PyPI's new releases to the watchlist
```

`--since` accepts `7d`, `2w`, `24h`, or an ISO date. PyPI discovery uses the timestamped RSS feeds, which hold only the latest 100 releases (`updates.xml`, about 20 minutes of PyPI) and the latest 40 new projects (`packages.xml`, about an hour). npm discovery reads the newest package names from npm's replication `_changes` feed (`replicate.npmjs.com`; 3 × `--limit` of them, 300 with `--limit 0`), then asks `registry.npmjs.org` when each one last changed and what its latest version is (the feed itself carries neither since npm's 2025 replication API change), newest first, until it has `--limit` packages or reaches the start of the window. `--limit` (default 50, `0` for none) caps the list across both registries. A package whose registry lookup fails is still listed, with its time estimated from the feed order.

Discovery says how much of the window it actually covered. When a feed or the npm walk doesn't reach back to the start of the window, or `--limit` leaves packages out, the heading says not all of the window was checked, a warning at the end names the part that was (`warning: discovery incomplete: pypi partly checked: covered 17:28–17:47 UTC only; its RSS feeds hold the latest 100 updates`), and `--ci` fails the run. If a feed can't be read, that registry is skipped with a warning, the summary says which registry was not (fully) checked, and `--ci` fails the run: a scheduled hunt never passes while checking nothing. Malformed feed rows and invalid package names are skipped with a warning, feeds are fetched under a 5 MB cap, and a package whose scan fails is counted as flagged (INCOMPLETE), never dropped. Full-ecosystem scanning of *every* package isn't offered (npm ≈3M / PyPI ≈600k) — use `--resume` for what is published from now on, a watchlist, or `--add` to build one up over time.

#### A scheduled hunt: `--resume`

A time window is only checked as far back as the feeds reach: a daily `discover --since 25h --scan --ci` covers about 20 minutes of PyPI (and says so). For a schedule, use `--resume`, e.g. a daily or hourly task running `discover --resume --scan --ci`, to catch newly published malicious packages before they land in your builds. Each registry then continues its change feed where the previous `--resume` run stopped, from a cursor kept in the state database (`--db`, table `discovery_cursors`):

- **PyPI:** one call per run to `changelog_since_serial` (PyPI's XML-RPC mirroring API, which it supports and rate-limits), read through the same host allowlist and time limit as every registry fetch, under a 32 MiB cap, and parsed with `lazaret.safexml`. Every release and new project since the last run is listed, each version: a release that was replaced by a clean one an hour later is still scanned.
- **npm:** the replication feed paged forward from the stored sequence number (10,000 changes a page, at most 20 pages a run), then one registry lookup per changed package for its latest version and time, as above.
- **First run:** a registry without a cursor checks the `--since` window as without `--resume` (so it may report partial coverage) and records where its feed is now; every later run covers everything since.
- **Runs that can't get through everything:** PyPI answers with at most 50,000 changes per call, npm's page budget is 200,000 changes, and `--limit` (with `--resume`: per registry, no limit by default, oldest first) may stop a run early. The run lists what it got, reports the registry as partly checked, `--ci` fails, and the cursor stays where it stopped, so the next run continues there. If that keeps happening, run the job more often.
- **Failures:** a registry whose feed can't be read is not checked and keeps its cursor. The cursor is stored only after listing, `--add` and `--scan` are done: a run that dies on the way leaves the old one, and the next run sees those packages again (versions already scanned are skipped).

Why a flag rather than using a cursor automatically: `--since` keeps meaning a time window. A one-off `discover --since 2h` neither jumps to a scheduled job's cursor nor moves it, which would make the job skip what the one-off listed; only `--resume` runs read and write the cursors. There is one cursor per registry per database, so run one `--resume` job per database. What it doesn't list: npm reports only each changed package's latest version, so an npm version superseded between two runs is seen only as its package's newest one; and PyPI files added to an existing release later (a new wheel) aren't changes of their own.

### Binary artifacts

Archives are classified file by file. Source files run through the normal ruleset; **binary/compiled files are inspected by content (magic bytes), not extension**, because smuggled binaries are a primary supply-chain vector — malicious code inside a compiled blob never appears in reviewable source. The scanner flags:

- **Executables / shared objects** (ELF, PE/DLL, Mach-O, WebAssembly, `.node`, `.pyc`, Java `.class`) — **MAJOR** (WARN) when found in a source distribution or npm tarball, but **INFO inventory** in a wheel, where compiled extensions are expected and the verdict stays OK.
- **A program under a source file's name** (an executable's bytes in a `.py` or `.js` file, such as a Windows executable named `_build.py`) — **CRITICAL** (SUSPICIOUS) in every kind of release, a wheel too, and in directory scans: no build ships one.
- **Nested archives** (zip/gzip/xz/tar inside the package) — a known way to hide a second-stage payload from review. Document formats that are archives by design (`.docx`, `.odg`, `.epub`, ...) are not flagged.
- **Opaque high-entropy blobs** — possible encrypted/packed payloads decoded at runtime. Recognized data assets (images including JPEG 2000 and Photoshop, fonts, ICC color profiles, audio, PDF) are not flagged.

Oversized binaries aren't loaded whole — only a header/entropy sample is read — so a large image or font is still classified, and doesn't make the scan INCOMPLETE. Only source files that would be scanned in full count toward INCOMPLETE, once per file however many times `package.json` names it. A source file over the size limit (`--max-source-bytes` / `LAZARET_MAX_SOURCE_BYTES`, default 16,000,000 bytes: an 8 MB minified bundle scans in about 5 seconds) makes the verdict INCOMPLETE; to settle one, re-scan that version with a higher limit and `--rescan`. Stylesheets, source maps, fonts and images that `package.json` exports are not code that runs; any other file it names is, whatever its extension, because `require()` runs a file with an unknown extension as JavaScript. A file the code requires is scanned if it is text, whatever its extension; an image or font it requires (React Native's `require('./icon.png')`) is an asset. The same magic-byte detection runs in directory scans on every non-source file, by content rather than name: a committed ELF renamed `logo.png`, a `.so`/`.exe`/`.node`, V8 bytecode (`.jsc`, bytenode), a nested archive or an opaque blob in your tree (or, with `--deps`, your dependencies) is flagged (**SC-BINARY**, SC-NESTED-ARCHIVE, SC-OPAQUE-BLOB).

### State backend

By default state lives in a local SQLite file (`lazaret-registry.db`, no dependencies). For a shared/persistent deployment, point it at PostgreSQL:

```bash
# Create a NEW dedicated database on your existing server — do NOT merge into
# an existing application DB (e.g. edgar). One-time setup:
psql -h HOST -U admin -c "CREATE DATABASE lazaret;"
psql -h HOST -U admin -d lazaret -f "$(python -c 'import importlib.resources as r; print(r.files("lazaret.registry") / "schema.sql")')"   # optional; the app self-creates tables too

export LAZARET_DB="postgres://lazaret_app:PASSWORD@HOST:5432/lazaret?sslmode=verify-full&sslrootcert=system"
lazaret-registry scan-all
```

`LAZARET_DB` (or `--db`) accepts a `postgres://`/`postgresql://` URL in any letter case, a libpq keyword string (`host=… dbname=… user=…`), `sqlite:PATH`, `sqlite:///PATH`, or a plain SQLite path; a path containing `=` is refused rather than silently becoming a SQLite file named after your DSN. libpq keepalive parameters (`keepalives_idle=…`) work in the DSN and are worth setting for long sweeps. A long-lived state connection (the MCP server, `scan-all`) reconnects once and retries once after a dropped session (admin shutdown, `idle_session_timeout`, a network blip) — never inside a transaction. Values the database can't store (a NUL byte, a non-UTF-8 file name) are escaped, so a hostile package can't make its own verdict unstorable.

`lazaret.pg` refuses to send an MD5 or cleartext password over TLS whose certificate wasn't verified (`sslmode=prefer`/`require`). Use `sslmode=verify-full` (or `verify-ca`) or a SCRAM-SHA-256 role. If you can't yet, `LAZARET_PG_ALLOW_MD5_OVER_UNVERIFIED_TLS=1` and `LAZARET_PG_ALLOW_CLEARTEXT_PASSWORD=1` are insecure escape hatches for the state DB (a DSN can't carry those options).

No driver install: the Postgres backend speaks the PostgreSQL wire protocol
directly (`lazaret.pg`, pure Python standard library — SCRAM-SHA-256
authentication and TLS included). The scanner uses a separate database so its `packages`/`scans` tables never collide with your other data; the same `LAZARET_DB` DSN is read by the MCP server for the `scan_package`/`registry_status` tools. Pair with `mcp__scheduled-tasks` (or cron) to run `scan-all --rescan` nightly across your dependency set.

## Guarding installs (`lazaret guard`)

Put `lazaret guard` in front of an install command. The packages it would install are fetched and scanned first, with the registry auditor's tests, and nothing is installed if one of them is SUSPICIOUS, can't be checked, or was published too recently to trust yet:

```bash
lazaret guard npm install express               # also: npm ci, npm update, npm install -g …
lazaret guard pnpm add react                    # also: pnpm install, pnpm update
lazaret guard yarn add lodash                   # yarn 1 and yarn 2+; also yarn install, yarn up, yarn remove
lazaret guard bun add zod                       # also: bun install, bun update, bun remove
lazaret guard pip install -r requirements.txt
lazaret guard uv add httpx                      # also: uv sync, uv lock, uv run, uv pip install, uv pip sync
lazaret guard uvx ruff check .                  # also: uv tool run, uv tool install
lazaret guard go get example.com/mod@v1.2.3     # also: go install, build, run, test, mod download, mod tidy
lazaret guard cargo add serde                   # also: cargo build, fetch, update, install, run, test
lazaret guard code --install-extension ms-python.python   # also: code-insiders, codium, cursor, windsurf, kiro, positron
lazaret guard code --update-extensions          # what the editor's own --update-extensions would update, checked
lazaret guard --plan npm install next           # resolve, fetch and scan; install nothing
lazaret guard --min-age 7d pnpm install         # hold back releases younger than a week
lazaret-guard npm install express               # the same command under its own name
```

**npm, pnpm, yarn, Bun and uv projects.** The package manager resolves first and installs nothing — your command with `--package-lock-only` (npm), `--lockfile-only` (pnpm, Bun) or `--mode=update-lockfile` (yarn 2+), `uv add --no-sync`, `uv lock` — with scripts off. yarn 1 has no such mode, so it resolves in a temporary copy of your project (its `package.json` files, `yarn.lock`, `.npmrc` and `.yarnrc`) with scripts off, and your project isn't touched until the checked install. Every package the new lockfile installs on this machine that isn't installed yet is fetched from where the package manager will fetch it (the lockfile's `resolved` URL, the scoped registry its settings name), checked against the lockfile's digest — so the bytes scanned are the bytes it will accept — and scanned in memory. (yarn 2+ records the checksum of its own zip of a package, not the tarball's, so there the tarball is checked against the digest the registry publishes; that checksum still lets a verdict be reused without a download.) If anything is blocked, the files the resolution changed (`package.json`, the lockfile, `pyproject.toml`, what yarn 2+ fetched into the project) are put back and nothing is installed. Otherwise your command runs as you typed it, and what it installed is compared with what was checked: anything else (the registry changed while the guard checked) is named and fails the run. Packages built for another platform (`os`, `cpu` and `libc`, the way npm reads them; yarn 2+'s `conditions`) are left out, and so are git dependencies, local folders and links, which are listed as not checked.

**pip, uv pip and uvx.** They install through an index the guard serves on 127.0.0.1, which relays the indexes they are set to use: pip's `index-url` and `extra-index-url` (all at once, as pip reads them), uv's indexes from its environment, `uv.toml` and `pyproject.toml` (the first that has a package, as uv reads them), and the ones you name on the command line (`-i`, `--extra-index-url`, `--index`, `--default-index`); `LAZARET_GUARD_PYPI_URL` stands for the tool's settings. It reads their JSON pages or their HTML (PEP 503) ones. Every file is scanned before the tool gets it, so an sdist is scanned before pip or uv can build it, which runs its `setup.py`; a blocked file is refused, and pip and uv install nothing unless every download succeeded. The tool's dry run (`pip install --dry-run --report`, `uv pip install --dry-run`) is scanned first. `uvx`, `uv tool run` and `uv tool install` resolve the tool's requirements through the guard's index first (`uv pip compile`: its files are scanned), then run as given, every download scanned before uv gets it. `uv run` in a project syncs the environment from `uv.lock` first, checked as `uv sync` is, then runs your command (with `--frozen`: the lockfile just checked); what else it installs (`--with`, a script's own dependencies) comes through the guard's index. The guard's index is uv's first, and it answers every package (an empty page for one no index has), so uv never goes on to an index in its settings files by itself (0.1.7 relayed PyPI only, and uv could fetch from such an index around it). Options that point pip or uv at local archives (`-f`, `--no-index`) are refused, and so are index options inside requirement files, which pip would use itself.

**Go (`lazaret guard go`).** The go command runs against a module proxy the guard serves on 127.0.0.1 for that one command (`GOPROXY` is set for it, with a secret path of the run's: the proxy answers no other path and no other `Host`, so nothing else on the machine can use it or your proxy's credentials), which relays the proxies your `GOPROXY` lists, in order and by go's rules (a comma goes on to the next proxy after a 404 or 410 only, a bar after any error), and scans each module zip before go gets it; a blocked one is refused with the reason. A zip is fetched once, to a file, and those bytes are what go gets: one over the 200 MiB the guard scans is INCOMPLETE, one over the 500 MiB go takes is blocked. go asks for several zips at once; they are fetched together and read and scanned within a budget of 512 MiB held at once (`LAZARET_GUARD_HOLD_MB`), so a dozen large modules never sit in memory together. go itself then checks the zip against `go.sum` and the checksum database, so what it accepts is what was scanned. `--min-age` leaves young versions out of a module's list and refuses their files, so `go get` takes the newest version old enough; a version whose time the proxy does not give is listed at the end of the run (and blocked under `--block-warn`). go takes some modules without asking the proxy: those it has in its module cache already (from a command the guard did not see) and those `GONOPROXY` (by default `GOPRIVATE`) names, which it fetches from their repositories. The guard lists what a command uses with `go mod download -json` and scans those zips where go keeps them: before `build`, `test`, `run` and `install` (so a hostile module in the cache stops the command before anything is built or run), and after `get`, `mod download` and `mod tidy`. A project that builds from its `vendor` folder fetches nothing, and the run says the guard checked nothing. `direct` in `GOPROXY` is not followed (the guard fetches nothing from version control, and says so). `GO111MODULE=off` and a `GOPROXY` of only `off` or `direct` stop the guard with a message. A toolchain download is checked by go against the checksum database and is not scanned (and the guard reads go's settings with `GOTOOLCHAIN=local`, so reading them downloads none). The module's Go code is read for what it does (see the registry section above): a module whose `init` code runs a download is SUSPICIOUS and blocked.

**Cargo (`lazaret guard cargo`).** cargo has no hook for a local server, so the guard resolves first (`cargo update --workspace`, or the lock as it is with `--locked` or `--frozen`), reads `Cargo.lock`, fetches every crates.io crate the lock names from where cargo would (the registry's `dl`, a `[source]` replacement's mirror, a `[registries]` entry one names, cargo's own cache), checks it against the lock's SHA-256 checksum, scans it, and only then lets cargo fetch and build — with `--locked`, so that it builds the lock that was checked. A crate cargo has unpacked already is checked too (another tool may have unpacked it; a verdict cached for its checksum is not scanned again), and a file in cargo's cache that is not the crate the lock names blocks: cargo builds a file it finds in its cache without checking it. cargo's configuration is read as cargo reads it: `.cargo/config` before `config.toml` in one folder, the files `include` names, and `--config`. For `add`, `update` and `generate-lockfile` the command is the resolution, and what it added to `Cargo.lock` is checked. `cargo install CRATE` resolves in a scratch project of its own, with the features you ask for, and installs `CRATE@=VERSION`, the version checked (with `--locked`, from the lock the crate was published with; a published lock the guard can't be sure of — two of them in the archive, one too large or unreadable — blocks). `--min-age` reads a release's time from the index (`pubtime`) or crates.io's API; one whose time is not known is listed at the end of the run (and blocked under `--block-warn`). A crate that can't be checked blocks; a crate from git, a vendor folder or a registry the guard can't read (or that asks for credentials) is INCOMPLETE, not checked, so `--block-warn` blocks it, and any crate cargo unpacked that the guard did not check is named, even when the build then fails. `Cargo.toml` and `Cargo.lock` are put back when anything is blocked, and after `--plan`. The guard's own runs of cargo take the command's `-Z` flags, so that they resolve as it will; with nightly's `--lockfile-path` the lock checked and put back is that one (`cargo install --lockfile-path` is refused). A crate from a plain-http registry on another machine that only `Cargo.lock` names, and not cargo's settings, is not fetched: it is INCOMPLETE, not checked. A download stops after 15 minutes in all, however often the server sends a byte (`LAZARET_GUARD_DOWNLOAD_SECONDS`).

**VS Code and the editors built on it (`lazaret guard code`).** An extension runs in the editor's extension host with all of your access and no sandbox, and most are installed from the editor's window, where no guard reaches (`lazaret --extensions` scans what is installed). `lazaret guard code --install-extension ID[@VERSION]` (or a `.vsix` file; also `code-insiders`, `codium`, `cursor`, `windsurf`, `kiro` and `positron`) does what the editor's own command does, up to the download, and then has the editor install what it checked. It takes the version the editor would install: an extension installed already is left alone unless `--force` or a version is given, as the editor leaves it; else the newest release (the newest version with `--pre-release` or `@prerelease`) that has a file for the editor's platform and whose `engines.vscode` takes the editor's VS Code version (its `--version`, or the `vscodeVersion` a fork's `product.json` names). It takes what that extension brings, as the editor walks it: its `extensionDependencies` that aren't installed and the members of its `extensionPack`, each at the version the editor would take, and what those bring in turn (built-in extensions count as installed; a dependency that can't be installed fails the extension that needs it, a pack member is left out; `--do-not-include-pack-dependencies` leaves them all out). The files come from the registry the editor installs from — the Visual Studio Marketplace for VS Code, Open VSX for the others, each Open VSX file checked against the SHA-256 Open VSX publishes; the editor's `product.json` names its gallery when the guard finds it beside the command (VSCodium's, also a `product.json` in its folder of user data and `VSCODE_GALLERY_SERVICE_URL`, as VSCodium reads them), and `--gallery vscode|openvsx` chooses; an editor whose gallery is one the guard doesn't read (a company's own) or none is refused unless `--gallery` says which registry to read for the extensions you name, since the guard would otherwise ask a public registry for each name and could install an extension of the same name that isn't the one your gallery has — and each is scanned as `lazaret FILE.vsix` scans it (what its `main` and `browser` modules run when the editor activates it, names like a popular extension's, `vscode:uninstall`), with `--min-age`, `--trust`, `--allow-new` and `--block-warn` as for the package managers, and against the list of extensions the editor's gallery has found malicious (Microsoft's, for the Marketplace's). Where that list says the editor installs another extension in place of one (an extension migrated to its pre-release, or VS Code's Copilot, for which it installs Copilot Chat), the guard checks and installs that one, as the editor would; one the list says is malicious is blocked as itself, as the editor refuses it before it looks for a replacement. If nothing is blocked, the editor installs those files (`--install-extension FILE.vsix`, from a folder of your own), with `--do-not-include-pack-dependencies` from VS Code 1.98 on so that it fetches nothing itself, and, before that, each extension after what it brings; `--profile`, `--extensions-dir`, `--user-data-dir`, `--force`, `--pre-release` and `--do-not-sync` are passed on. Then what the editor lists as installed is compared with what was checked, and anything else is named and fails the run. An extension installed from a file is pinned by the editor, as one installed with `@VERSION` is: it stays at the version checked until you update it. `lazaret guard code --update-extensions` updates what the editor's own `--update-extensions` would update, checked and installed the same way: each extension the editor lists that came from its gallery — which, and whether it follows pre-releases, is what the editor recorded when it installed it (its profile's `extensions.json`; with `--profile`, that profile's) — to the newest version the editor would take for it, with what that version brings. It runs only when the guard reads the gallery the editor installs from (not with `--gallery` naming another: every extension installed would be asked for by name). The editor asks its gallery by the identifier it recorded, so an extension whose name the gallery now gives to another one (another identifier) is left alone, and said; one installed from a file has no identifier until the editor's window matches it to its gallery by name, so the guard matches it by name too, and the extensions it installed are updated by it (the editor's own `--update-extensions` passes over them until its window has opened). With `--min-age`, an update younger than that is held back and the newest version old enough is taken, if it's newer than the one installed. An extension installed in every profile is updated in the default profile, where the editor keeps it, and one that follows pre-releases is installed with `--pre-release`, as the editor's own update installs them. Nothing is installed if anything is blocked or a lookup fails. VS Code checks the signature of a Marketplace extension it downloads itself, and not of a file it is given, so under the guard that check does not run: the guard checks that the file is the extension and version the registry named, and scans it, and what the editor installs is the file that was scanned.

**The guard's own folders and programs.** A resolution the guard makes outside your project (`cargo install`, yarn 1, `npm install -g`, a Go install of `pkg@version`, `--plan`) is made in a folder of your own: `LAZARET_GUARD_SCRATCH`, else your cache folder (`~/.cache/lazaret/tmp`), else a temporary folder only you can write above. cargo, rustup, yarn, npm and go read settings from every folder above where they run, and a shared `/tmp` is one any user on the machine can write to. The package manager is the one your `PATH` names by an absolute path, never one in the current folder (on Windows a project's `go.exe` or `npm.cmd` would otherwise run in its place); `lazaret hook` finds `git` the same way.

**Private registries and indexes.** The guard fetches with the credentials your package manager's own settings give: the `.npmrc` keys npm, pnpm, yarn 1 and Bun read (`//host/path/:_authToken`, `_auth`, `username` and `_password`, with `${VAR}`), yarn 2+'s `npmAuthToken` and `npmAuthIdent` (top level, `npmScopes`, `npmRegistries`), Bun's `bunfig.toml` (`[install] registry` and `[install.scopes]`: a token or a login), a Python index URL's `user:password@`, uv's `UV_INDEX_<NAME>_USERNAME` and `_PASSWORD`, and `.netrc`. Each credential goes only to the host — and for npm's keys the path — it is set for, over https (or plain http to this machine), never on a redirect to another host, and never into the guard's output, cache or `--json`. pip and uv get the packages from 127.0.0.1 without credentials.

**Release age.** Malicious releases of popular packages are usually found and pulled within hours to days of publishing, so waiting a couple of days before taking a new release avoids most of them. `--min-age` (default `2d`; `0` turns it off) holds back releases younger than that where the tool can do it without changing your lockfile — npm's `before` (npm then picks the newest older release), pnpm's `minimum-release-age` (pnpm 10.16+), yarn's `npmMinimalAgeGate` (yarn 4.10+), Bun's `--minimum-release-age` (Bun 1.3+), and for pip, uv pip and uvx by leaving new files out of the local index (an index whose HTML pages give no upload times can't be held back; the report says so) — and blocks them otherwise: a release a lockfile already pins (`npm ci`, `uv.lock`), aged by its tarball's `Last-Modified` confirmed by the registry's publish time, or uv.lock's upload time. npm always resolves with `before` set (to the start of the run when `--min-age` is `0` or `--allow-new` is given), so the install can't pick a release the guard didn't check; a stricter `before` of your own is kept.

**What blocks.** SUSPICIOUS blocks, and so does a package that couldn't be fetched, verified or scanned (the guard fails closed). So does an INCOMPLETE one whose scan couldn't read what a package can be made to hide: the scan ran out of time (it's scanned once more first, and a time-out is never cached), the engine couldn't finish reading it, code that runs or a source file was cut at a limit (a payload padded past the size limit inside its file) or is bytecode no one can read (a bytenode `.jsc` run at install), or the archive couldn't be read whole; `--allow-incomplete` lets those through. WARN and the other INCOMPLETE verdicts (a file over the 200 MiB download limit, a program too large to read, such as a 16 MB native library) are listed and don't block unless you pass `--block-warn`. Two overrides, each repeatable and taking patterns like `'@corp/*'`:

- `--allow-new NAME` lets NAME's new releases through the age check. They are still scanned.
- `--trust NAME` installs NAME whatever the guard finds or can't check: a finding you have reviewed, or a package it can't fetch. It is still listed in the report.

**Speed.** A verdict is cached by the artifact's digest and the engine version (`~/.cache/lazaret/guard-verdicts.json`, or `$XDG_CACHE_HOME`, or `LAZARET_GUARD_CACHE`; `--no-cache` or `LAZARET_GUARD_CACHE=/dev/null` to skip), so a package is fetched and scanned once, and a repeat `npm ci` downloads nothing. Downloads run in parallel and scans in worker processes (`--jobs`, default up to 4), `--jobs 1` included: a worker gets the archive as a file, hashed again before it is read, an address-space limit (`--worker-memory MB`, default 6144; Linux) and its share of the cores, so a scan that grows too large cannot take the guard down. A worker that dies has its archives scanned again, each alone; one that kills its worker twice blocks its package as not checked. `--no-isolate` scans in the guard's own process, for a platform where workers can't start (the guard falls back to that by itself, and says so). `--from-plan` (pip, opt-in) installs the files that were scanned from a folder instead of letting pip resolve and download again: on `requests`, `boto3` and `pydantic` the guarded install took 13.5 s instead of 19.2 s; a plan with an sdist goes through the guard's index as before. `--keepalive` (experimental) reuses the guard's connections; `--timings` shows where a run's time goes and how many connections it made and reused. On a 2-core Linux machine, a first guarded install of `express` (66 packages) takes about 5 seconds; `next`, `react`, `react-dom`, `typescript` and `eslint` about 53 (50 with 0.1.7, on the same versions), most of it spent scanning the `next` tarball.

**Provenance (npm and PyPI).** A release from npm's or PyPI's public registry that was published in the last 30 days (or whose publish time isn't known) also gets the registry's provenance check: its attestations (npm's publish attestation and SLSA provenance, PyPI's PEP 740) verified against Sigstore's trust and npm's keys, and compared with the release before it. An attestation that doesn't hold for the file is SUSPICIOUS and blocks the install; a release with none of the provenance the release before it had (as ultralytics 8.3.45 and 8.3.46, uploaded with a stolen token) is WARN and blocked, as pnpm's `trustPolicy: no-downgrade` fails such an install (`--trust NAME` lets one through); one with provenance from another owner's repository is WARN (`--block-warn` blocks it). Whether a release has provenance is the release's: a PyPI file without it, beside files of the same release with it, is not a release published without it. Older releases are left out: a hijacked release is found and taken down within days as a rule, and the check reads the package's history. A private registry's packages are never named to the public one. A verdict cached while the registry's answers couldn't be read, or with the check off, is checked again while the release is in that window. `LAZARET_NO_PROVENANCE=1` turns it off.

`--json PATH` writes every package checked, its verdict, findings, age and digest (`generatedBy: lazaret-guard-1`). Exit codes: 0 installed (or nothing to do), 1 blocked, or installed something it didn't check, 2 usage error, 3 the resolution failed, otherwise the package manager's own. Not wrapped: `npx`/`npm exec`, `pnpm dlx`, `yarn dlx`, `bunx`, pnpm's and Bun's global installs, `yarn global`, and `uv add --script` or `uv lock --script`.

## MCP setup (use Lazaret to test changes)

1. `pip install lazaret` into the Python the MCP client will launch.
2. Copy `examples/mcp-config.json` and replace `/ABSOLUTE/PATH/TO/lazaret-registry.db` in the `env` block
   with the absolute path where the registry state DB should live. An absolute DB path matters: the MCP
   server resolves a relative one against whatever directory the client launched it in, so a relative
   path silently creates a NEW empty DB (or finds a different one) instead of the one your `scan-all`
   sweeps write.
3. Decide what the path tools may read. `scan_directory`, `scan_files` and `quality_gate` read only
   inside the roots your MCP client shares (Claude Code shares the directory it was started in and any
   added with `--add-dir`), or inside the directories you list in `LAZARET_MCP_ROOTS` in the `env`
   block, which take precedence. If the client shares none and the variable is unset, those tools
   return an error that says so.
4. Register the server:
   - **Claude Code**: copy the `lazaret` entry into your project's `.mcp.json`
     (or run `claude mcp add lazaret -- lazaret-mcp`)
   - **Claude Desktop**: merge the entry into `claude_desktop_config.json`
     (Settings → Developer → Edit Config), then restart the app.

### Tools exposed

- `scan_directory(path, exclude?, include_deps?, max_issues?)` — full project scan: gate, metrics, ratings, issues
- `scan_files(paths)` — scan just the files you changed (config files such as `.env` or `.yaml` are checked for credentials)
- `scan_snippet(code, language)` — check code before writing it to disk
- `scan_package(spec, full?)` — fetch and audit a public npm/PyPI package (e.g. `npm:left-pad@1.3.0`)
- `registry_status()` — tracked packages and their latest verdicts
- `discover_packages(since, ecosystem?, scan?, limit?)` — find npm/PyPI packages newly published/updated in a recent window, optionally scanning them
- `quality_gate(path)` — compact PASSED/FAILED check after making changes

Typical workflow: edit code → `scan_files` on the changed files → fix findings → `quality_gate` on the project.

### Limits and safety

The MCP client is a model, and a model can be steered by content it has read, so the server bounds what a tool call can do:

- **Allowed roots:** the path tools read only inside `LAZARET_MCP_ROOTS` (paths separated by `:` — `;` on Windows) when it is set, and otherwise inside the roots the MCP client shares, asked for with `roots/list` and asked again when the client says they changed. A path outside the roots is a tool error, and with no roots at all every path is refused with an error that says how to allow one. Set but empty (only separators or spaces), every tool call is refused as a configuration error. Before 0.1.7 an unset `LAZARET_MCP_ROOTS` allowed any path the server's user could read.
- **Per-call caps:** `LAZARET_MCP_MAX_FILES` (default 20,000), `LAZARET_MCP_MAX_BYTES` (200,000,000) and `LAZARET_MCP_MAX_SECONDS` (300). A call that hits one returns what it scanned, marked `"incomplete": true` with an SC-TRUNCATED finding (in `scan_files`, one for each file left out), so it can never pass the gate. `discover_packages` with `scan` scans at most 15 packages per call; the rest, and any past the deadline, come back as INCOMPLETE "not scanned" entries. A directory that doesn't exist or can't be listed is a tool error; a directory with nothing Lazaret scans, and a `scan_files` path that exists but can't be read, come back incomplete with an SC-TRUNCATED finding, never as a clean pass.
- **Credentials:** a registry tool (`scan_package`, `discover_packages`) never stores or returns a raw credential line; findings carry a placeholder. `LAZARET_NO_REDACT=1` turns redaction off for the project tools only (`scan_directory`, `scan_files`, `scan_snippet`, `quality_gate`), which read your own code.
- **Responsiveness:** tool calls run on a worker thread; `ping` is answered while a scan runs, and `notifications/cancelled` stops the scan between files.
- **Same pipeline as the CLI:** `scan_directory` and `quality_gate` run exactly what `lazaret <dir>` runs (`lazaret.scanner.core.scan_project`), including `binding.gyp` hooks, pruned-tree notes and the cross-file pass.
- **Protocol:** JSON-RPC 2.0 over stdio; protocol versions 2025-11-25, 2025-06-18 and 2024-11-05 are negotiated; malformed JSON gets a -32700 error, notifications are never answered, and stdout carries protocol frames only.

## Postgres connector (`lazaret.pg`)

A PostgreSQL client written in pure Python, using only the standard library, so lazaret keeps zero runtime dependencies.

```python
from lazaret import pg

with pg.connect("postgresql://lazaret@db.example.com/lazaret",
                sslmode="verify-full", sslrootcert="system") as conn:
    conn.execute("INSERT INTO scans (package, verdict) VALUES ($1, $2)", "requests", "ok")
    rows = conn.fetch("SELECT package, verdict FROM scans WHERE verdict <> $1", "ok")
    for row in rows:
        print(row.package, row["verdict"])

    with conn.transaction():             # commit on success, roll back on exception
        conn.executemany("INSERT INTO seen (name) VALUES ($1)", [("a",), ("b",)])

    for row in conn.iterate("SELECT * FROM big_table", batch_size=1000):  # streams
        ...
```

API: `execute`, `fetch`, `fetchrow`, `fetchval`, `executemany` (pipelined and atomic; result rows such as `RETURNING` are discarded, and an error raised at commit — a deferred constraint, a serialization failure — is raised, never lost), `iterate` (streaming; also raises commit-time errors, and ends cleanly when its `transaction()` block exits or the connection closes), `execute_script` (multi-statement migrations), `transaction()` (nested blocks use savepoints), `cancel()` (thread-safe), `reconnect()` (same parameters), `register_decoder()` for custom types (a decoder that fails falls back to the text value instead of breaking the connection), plus `notice_handler` and `notifications` for LISTEN/NOTIFY. A server that ends the session (admin shutdown, `pg_terminate_backend`, `idle_session_timeout`) raises `ServerOperationalError` with its SQLSTATE; errors pickle and copy, so they cross process boundaries.

Parameters: Python `int` is sent as `int4`, `int8` or `numeric` by size, so functions like `repeat(text, int)` resolve; lists of `str` are sent untyped (use a cast for polymorphic functions: `unnest($1::text[])`); `timedelta` is encoded with a sign on every field, so it means the same under every `IntervalStyle`.

Connection settings follow libpq: a `postgresql://` URL (parsed the way libpq parses it: an unencoded `#` or `?` in a password is part of the password, `+` is not a space) or `key=value` string, keyword overrides, `PG*` environment variables, and `~/.pgpass` (only the default Unix-socket directories — `/tmp`, `/var/run/postgresql`, `/run/postgresql` — match `localhost`; other socket directories match their own path). Implemented libpq parameters include `hostaddr`, `connect_timeout`, `keepalives*`, `tcp_user_timeout`, `target_session_attrs`, `application_name`/`fallback_application_name`, `client_encoding` (UTF8), `sslpassword`, `sslcertmode`, `sslcrl`/`sslcrldir`, `sslsni`, `ssl_min_protocol_version`/`ssl_max_protocol_version` (never below TLS 1.2), `requiressl` and `requirepeer` (Linux); GSS/OAuth/load-balancing parameters are accepted with a warning and ignored; `service` and `replication` are refused. libpq's default client certificate and key (`~/.postgresql/postgresql.crt`/`.key`) and CRL are used when present; an encrypted client key without `sslpassword` is an error, never a terminal prompt.

Security behavior:
- **No SQL injection by construction.** Queries use the extended protocol with `$1, $2, ...` placeholders, so values travel separately from SQL and are never spliced into it.
- **TLS** with `sslmode` `disable` / `prefer` (default, as in libpq) / `require` / `verify-ca` / `verify-full`, TLS 1.2 minimum. Use `verify-full` for anything beyond localhost. As in libpq, `require` verifies the chain (like `verify-ca`) when `sslrootcert` is set or `~/.postgresql/root.crt` (`%APPDATA%\postgresql\root.crt` on Windows) exists. `sslrootcert=system` (public CAs) is only accepted with `verify-full`, since `verify-ca` against public CAs would accept any publicly issued certificate; given alone, it selects `verify-full`.
- **SCRAM-SHA-256** with SASLprep (matching PostgreSQL's own, so Unicode passwords log in), and **channel binding** (`tls-server-end-point`) automatically over TLS. `channel_binding=require` enforces it.
- **No password for an unverified server:** under `prefer` or `require` without a verified certificate, a man-in-the-middle that terminates TLS could simply ask for the password in cleartext or MD5. Lazaret refuses both over unverified TLS (opt back in with `allow_cleartext_password=True` / `allow_md5_over_unverified_tls=True`), so SCRAM with channel binding is the only thing such an attacker gets to see, and that can't be relayed. Under `prefer` an active attacker can still strip TLS entirely; use `verify-full` or `require_auth="scram-sha-256"` for real protection.
- The server must prove it knows the password: a server that skips the SCRAM final step or sends a forged signature is rejected.
- `require_auth` (as in libpq) pins the allowed methods, e.g. `require_auth="scram-sha-256"` to refuse downgrades to MD5, cleartext, or no authentication.
- A **cleartext password is never sent over unencrypted TCP or unverified TLS** (only over a Unix socket or `verify-ca`/`verify-full`) unless you pass `allow_cleartext_password=True`.
- `~/.pgpass` is ignored if it's readable by group or others, and passwords never appear in `repr()` or error messages.
- Defensive parsing: oversized messages, unexpected messages, malformed messages and protocol violations close the connection with a `pg.Error` rather than being trusted. Pipelined `executemany` reads replies while it writes, so a chatty server can't deadlock it.

Not supported: COPY (refused cleanly; the connection stays usable), GSSAPI/SSPI/Kerberos (parameters accepted and ignored), service files, multiple hosts, and replication.

## Safe XML parsing (`lazaret.safexml`)

A defusedxml-style layer over the stdlib XML parsers, also standard-library only. Use it for any XML that comes from outside, such as CycloneDX SBOMs, package metadata, feeds, and XML-RPC responses. Module names mirror the stdlib and defusedxml, so switching is one import line:

```python
from lazaret.safexml import ElementTree as ET     # instead of xml.etree.ElementTree
root = ET.fromstring(untrusted_bytes)             # returns normal ElementTree objects
for event, elem in ET.iterparse("sbom.xml"):      # streaming works too
    ...

from lazaret.safexml import minidom, sax, pulldom, xmlrpc
proxy = xmlrpc.ServerProxy("https://pypi.org/pypi")   # safe XML-RPC client
```

What it blocks, in every API (ElementTree, minidom, SAX, pulldom, XML-RPC):
- **Entity bombs** (billion laughs, quadratic blowup) and **XXE** (reading local files, server-side requests), by refusing entity declarations. `EntitiesForbidden`
- **Attribute-default blowup**: `<!ATTLIST>` defaults are copied onto every matching element, a quadratic blowup that needs no entity at all. Declared defaults are budgeted (`max_attlist_defaults`, 65,536 characters in total plus 64 per declaration), and once any default is declared the attributes reported may not exceed 100× the input after 8 MiB. `LimitExceeded`
- **Content-model crashes**: `<!ELEMENT>` content models are never converted (pyexpat does that recursively in C, and a deeply nested model crashed the interpreter).
- **External entity references.** `ExternalReferenceForbidden`
- **External DTDs and parameter entities are never loaded**, in any API, with any options. A DOCTYPE that points to an external DTD is accepted but ignored. The tests prove this with a local HTTP server that must receive zero requests.
- **Deep nesting**: `max_depth`, 500 by default. `LimitExceeded`
- **Oversized input**: `max_bytes`, unlimited by default, except 32 MiB for XML-RPC responses. The XML-RPC cap is measured after gzip decompression, and gzip replies are decompressed while they are read with the compressed size capped too (`max_bytes` + 1% + 64 KiB), so "zip bomb" responses are cut off without buffering them. Error replies are read only when their declared length is ≤ 8 KiB, and never past 8 KiB whatever the headers say (a chunked body makes http.client ignore Content-Length); otherwise the connection is closed.
- Optionally, any DOCTYPE at all: `forbid_dtd=True`. `DTDForbidden`. This is the default for XML-RPC (`loads`, `ServerProxy`, `Transport`, `monkey_patch`), which never legitimately carries a DOCTYPE.

Options and exception names match defusedxml (`forbid_dtd`, `forbid_entities`, `forbid_external`, `DefusedXmlException`), and refusals are `ValueError` subclasses. On normal documents, output is identical to the stdlib's; the compatibility tests compare them directly.

`lazaret.safexml.ElementTree` exports every name in `xml.etree.ElementTree` — the non-parsing ones (`Element`, `SubElement`, `tostring`, …) are the stdlib's own objects — plus safe `XMLParser`, `XMLPullParser`, `iterparse`, `XMLID`, `canonicalize` and an `ElementTree` class whose `parse()` is safe. A `parser` argument must be a safexml parser (for minidom and pulldom, one from `safexml.sax.make_parser()`), otherwise `TypeError` — never a silent fallback to an unsafe parser. In `iterparse` and `XMLPullParser`, errors and refusals are raised after the events that precede them, and `flush()` works as in the stdlib.

Differences from defusedxml:
- It adds `max_depth`, `max_bytes` and `max_attlist_defaults`, and XML-RPC `ServerProxy`/`Transport` classes, in addition to the global `xmlrpc.monkey_patch()`.
- minidom's `Text.isWhitespaceInElementContent` is always False, because content models are not converted.
- The minidom builder classes (`SafeExpatBuilder`, `SafeExpatBuilderNS`) refuse `xml.dom.xmlbuilder.Options` with a `filter` (`NotSupportedError`): while it filters, the stdlib builder replaces the handlers that enforce the protections.
- `forbid_entities=False` is only allowed when the Python's libexpat is 2.4.1 or later, whose built-in amplification limit still stops entity bombs. Otherwise it raises `NotSupportedError`.
- The stdlib SAX reader asks for external DTDs, so defusedxml's SAX API rejects documents that merely reference one. Here every API behaves the same way: the reference is ignored and nothing is loaded.
- It has no lxml support and no global `defuse_stdlib()` patching.

Never call `xml.etree.ElementInclude.include()` on untrusted documents; XInclude loads the files it points to, and that isn't covered here.

The codec names the npm package and the dashboard list are what Python's codecs answer to: facts about Python, not CPython's code.

- **Build:** `python/pyproject.toml` declares no build requirements; a small standard-library backend in `python/_build/` produces the wheels and sdist, compiling the engine with cargo where no library is given (from source; the workspace has no crates to fetch). `pip install` works with no network index.
- **Tests:** plain `unittest`; the whole suite runs on a stock interpreter.
- **Native engine** (0.1.8; the only engine since the Rust-first refactor): every wheel carries a library built from `rust/` — the platform wheels for Linux x86-64 and ARM64, macOS arm64 and x86-64 and Windows x64, which release CI builds each on its platform (the Linux ones in PyPA's manylinux_2_28 images); elsewhere pip compiles it from the sdist. It runs the install-script and import-time tests, the per-file rules (the supply-chain and credential rules of `--deps`, registry and guard scans whole; in your own project the rules part, before the taint, SQL and function passes) and the cross-file follower, on several threads, and the npm package runs the same engine as WebAssembly. It is written with **no external crates** — its own linear-time regex engine with `re`'s answers, which runs every pattern, JSON and Unicode tables — and `scripts/check_rust_deps.py` fails CI if a crate from outside the repository appears. Until the refactor it was held to the Python engine answer for answer (differential tests on every pattern, ~36,900 hook cases and the per-file scan's corpus, and file by file on the benchmark's 55,161 source files: no difference); now it is held to its own recorded outputs, so a change to what it finds is a reviewed difference (`docs/RUST_ENGINE.md` §5). A file it can't finish (a hostile input that spends its work budget) is SC-TRUNCATED, which fails the gate. `--version` names it: `lazaret 0.1.8 (engine: rust 0.1.8)`; without it the scanning commands stop with exit code 2.

Its engine is its own JavaScript port of the project scanner, not the npm package's WebAssembly engine (uploads may include `.pth` files, which get the SC-PTH-EXEC check) and reports the same per-file findings as the CLI (the cross-file pass is the CLI's; and the page keeps its own comment lexer, which reads a template's `${…}` and an f-string's fields as text where the engine's lexers read them as code), redacts secrets the same way, and exports under its own name (`lazaret-dashboard-export.json`, marked `generatedBy: lazaret-dashboard-1`) so an export is never mistaken for a CLI report.

Tests enforce this: `tests/architecture/test_stdlib_only.py` fails on any non-stdlib import in the package or the build backend, and `tests/build/test_build_backend.py` checks that the wheel declares no dependencies. Test fixtures that mention third-party packages (`flask`, `requests`, `evil-pkg` …) are scan *targets*; nothing imports them.
