# tiny_https backlog

Status: a complete, working HTTPS client. Crypto, X.509 validation, the TLS 1.3 handshake (and TLS 1.2 for servers that speak nothing newer), the
HTTP/1.1 layer (keep-alive pool, streaming bodies) and an opt-in HTTP/2 client are written and tested; behind the opt-in
`server` feature there is also a small TLS 1.3 and HTTP/2 server that the tests and interop scripts use as a peer. Last full run (suites run one at a time, each well under
45 s): 1,260 unit tests (and 17 more that are `#[ignore]`d by default: 13 timing tests, two long random runs, a live QPACK peer and a replay of fuzz inputs; 297 of the unit tests also run without the `net` feature), 2 Go-vector tests (`tests/go_vectors.rs`, pure), 1 CMS-vector test (`tests/cms_vectors.rs`, pure, 1,886 cases judged by OpenSSL), 2 inflate-vector tests (`tests/inflate_vectors.rs`, pure, 256 streams from other compressors and 1,039 damaged ones with zlib's verdicts), 6 real-chain tests (`tests/real_chains.rs`, 52 chains captured on a normal network, B-97), 13 real Sigstore attestation tests (`tests/sigstore_real.rs`), 5 synthetic Sigstore bundle tests (`tests/sigstore_synthetic.rs`, 86 bundles), 3 real Rekor tests (`tests/rekor_real.rs`), 47 OpenSSL interop tests (12 of them TLS 1.2), 17 HTTP/2 client tests against Go's own server (2 of them over TLS 1.2) (`tests/h2_client_interop.rs`), 22 HTTP/3 client tests against aioquic (`tests/h3_client_interop.rs`), 1 real-root-certificate
test, 14 doc tests, zero compiler warnings, on x86-64 Linux. An Apple M5 Max (aarch64 macOS) passed the whole suite natively
before the async work (B-58). The unit tests also passed under emulation for 64-bit ARM (the NEON path),
32-bit ARM and with the portable path forced on x86-64 at an earlier revision; that has not been re-run since the
TLS and async refactors (see "Portability" in the README).

What the tests actually prove:

- `tests/interop_openssl.rs` handshakes with `openssl s_server` using RSA, P-256, P-384 and Ed25519 server
  keys (and an Ed25519 CA issuing Ed25519, P-256 and RSA server keys, and a P-256 CA issuing an Ed25519 one) with each of the three cipher suites, checks hostname, IP and untrusted-CA rejection, clock
  override, ALPN, byte-exact 3 MiB downloads and 1.2 MB uploads on all
  three cipher suites, downloads over a transport that returns 1 to 20,000 bytes per read, and the
  HTTP client over TLS. Over TLS 1.2 (`-tls1_2`): every suite, key type and group, bulk both ways, certificate checks,
  revocation, what is not offered, and two men in the middle (a downgrade the check catches, an extended master secret taken out).
- `tools/server_interop.sh` runs the in-crate TLS server (`examples/serve`) against `openssl s_client`, curl and a Go
  client (`tools/server_interop.go`) with each cipher suite and group, record fragmentation, rekeys, ticket counts
  and ALPN: 36 checks, and the server's own log must show no complaint. `tools/h2_interop.sh` does the same for the
  HTTP/2 server on top of it: curl (nghttp2), Go's `net/http` client (`tools/h2_interop.go`, 24 checks in each of
  five configurations) and python-h2, which raises on any frame a server should not send (`tools/h2_interop.py`,
  21 checks in each of three configurations): 21 checks of the script in all. The reverse direction is `tests/h2_client_interop.rs`: our HTTP/2 client against
  Go's own HTTP/2 server (`tools/h2_oracle_server.go`, built with `go build` when `go` is installed, skipped if not).
- HPACK is checked against RFC 7541 appendix C and in both directions against Go's `hpack` and Python's `hpack`
  (`tools/hpack_oracle.go`, `tools/hpack_oracle_go.sh`, `tools/hpack_oracle.py`: blocks made by those encoders are in
  `tests/data`, and what our encoder writes is decoded by them); the frame layer's fixtures come from hyperframe
  (`tools/h2_frame_oracle.py`).
- The AEAD ciphers and Poly1305 are checked against vectors from an independent implementation
  (Python `cryptography`, regenerated by `tools/gen_aead_vectors.py`), including lengths around every
  block and record boundary and Poly1305 edge cases near 2^130 - 5.
- `tests/system_roots.rs` parses all 128 certificates in the system CA bundle and verifies the
  122 self-signatures that use supported algorithms (RSA up to 4096 bits, ECDSA P-256/P-384) with
  our own code: zero failures. The 5 skipped use SHA-1 and 1 root uses P-521.
- `fuzz/` is a coverage-guided fuzzer (44 targets, std-only, stable Rust; B-12). It found five real bugs
  in its first minutes, one of them a way around the response size limit in release builds; each has a
  regression test. Only about a minute per target has been run since, so it shows the engine works,
  not that the parsers are clean: hours of it on the Mac are B-66.
- The sandbox gateway also completed handshakes and HTTP fetches for pypi.org, registry.npmjs.org,
  index.crates.io, jsr.io and proxy.golang.org (a third TLS implementation). **Caveat:** that
  gateway re-signs TLS with its own CA, so those runs did not exercise real public CA chains such as
  Let's Encrypt or Google Trust Services. See B-08.

Size key: S = under half a day, M = about a day, L = several days.

## Requests from a consumer (Lazaret: a package-security scanner)

A scanner that reads registry metadata and downloaded packages asked for three things, in this order of
value: (1) verification of signatures and certificate chains, to check where a release came from; (2) one
fast network layer for registry, advisory-feed and secret-verification traffic; (3) a scanning HTTPS proxy
for any package manager. Its constraints: the scanning engine stays pure (no sockets, no `unsafe`), network
code lives in its own crate, no outside dependencies, a licence compatible with Apache-2.0, and no reliance
on hand-written TLS until it has been independently reviewed. Proposed order: B-77, B-69, B-67, B-68 and B-70 phase 1 and B-71 (done; B-68 delivers the Go checksum database check, B-70 CMS signatures and time stamps, B-71 Sigstore bundles), then, in parallel,
B-56, B-46, B-74, B-75, then B-72; B-78 only after B-23.

What already serves these asks: the X.509 parser and chain verifier (RSA PKCS#1, ECDSA P-256/P-384 with
SHA-256/384/512, and Ed25519), signed notes, Merkle proofs, the Go checksum database check (B-68), CMS / PKCS#7 signatures and RFC 3161 time stamps (B-70), Sigstore bundle, npm and PyPI attestation verification with a strict JSON parser (B-71), SHA-2, HMAC, PEM, the DER reader, name constraints, revocation (B-32), a std-only HTTP/1.1
client with proxy support, redirects with credential stripping, a thread-backed and a non-blocking async
layer, a sans-IO TLS connection (`tls::ClientConnection`: bytes in, bytes out) that any caller can drive, a keep-alive pool and streaming bodies (B-46, B-56), and an HTTP/2 client for the blocking `Client` (B-72 part 1).
What does not exist: Authenticode and Apple code signatures (B-70 phase 2), certificate transparency (SCT) checks and fetching the trusted root through TUF (B-81, B-82), HTTP/2 for the async client (B-72 part 2), inflate, and any TLS-server or signing code fit for production (the test server of B-83 is not). A verifier that wrongly accepts is the dangerous failure, so every item below
needs negative vectors (malformed and malleable signatures, wrong algorithm, wrong key) and a fuzz target
besides the positive tests, and real artifacts captured offline as fixtures (as B-08 and B-65 do for TLS).

## Known limitations (by design, for now)

- `unsafe` appears only behind the `net` feature (the pure verification part is `forbid(unsafe_code)`): in the SIMD kernels (AES-NI/ARMv8 AES and carry-less multiply in `aes_hw.rs`, GHASH, and the ChaCha20 vector backends), the operating-system random calls in `crypto::rand`, and the volatile write in `util::Zeroize`; each has a SAFETY comment. Building with `RUSTFLAGS="--cfg tiny_https_portable"` removes the SIMD kernels. Nothing in parsing, X.509, ECDSA, RSA or the TLS state machine uses it (B-77 makes that checkable with `forbid(unsafe_code)`).
- Each connection holds a 64 KiB receive buffer and, while writing, up to about 66 KiB of write buffer (an HTTP/2 connection also has a 128 KiB read buffer in its reader thread).
- HTTP/1.1 by default (ALPN offers `http/1.1`); HTTP/2 only when asked for with `Client::http2(true)`, and only for the blocking client (and the `*_async` methods that run it), not for `AsyncClient` (B-72 part 2). Connections are reused (a keep-alive pool; one shared connection per origin for HTTP/2). HTTP/2 responses have no reason phrase and their trailers are dropped; server push is refused and priorities are ignored. Responses are decoded (`gzip`, `deflate`) only when asked (`decompress`, B-37); plain-http requests are refused unless `allow_insecure_http(true)`; proxies are used for https URLs only.
- An HTTP/2 connection reads and decrypts on one thread (about 170 MB/s on the test machine), and may hold up to its 32 MiB connection window of body that the application has not read yet. It costs two threads for as long as it is open.
- The TLS and HTTP/2 server (`server` feature) is a test peer, not a product: Ed25519 signing that is not constant time, no resumption, no client certificates, one certificate, no review (B-83).
- TLS 1.3, and TLS 1.2 with a server that speaks nothing newer (ECDHE and AEAD suites only, the extended master secret required, no renegotiation, no resumption; B-36), unless the client or the request asks for 1.3 only; key exchange with X25519, P-256 or P-384 (in 1.3 a share for the first, the others after a HelloRetryRequest); no client certificates (an empty Certificate is sent when asked); no session resumption in either version (B-35).
- Revocation is checked only with a stapled OCSP response and with CRLs that are supplied or fetched from the leaf's distribution point; there is no OCSP client, so soft-fail (the default) is blind to a revoked certificate on a server that does not staple (B-63, B-64).
- Trust roots come from a PEM bundle file; there is no native Windows or macOS store access.
- A connection that ends without `close_notify` is reported as an error (truncation protection).
- Unaudited cryptography; not for production use with sensitive data until B-23 (independent review) is done.
